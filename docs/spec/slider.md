# Slider

One `##` section covering single-thumb and multi-thumb sliders. The APG splits
them into the slider and multi-thumb slider patterns; every library treats them
as one component with an array value, so the spec does too.

Bullets tagged `[apg]`, `[html]` or `[axe]` come from a standard or a linter
rather than a library, so they are normative and never carry `(candidate)`.

## slider

### Roles and attributes

- [ ] `slider.roles-and-attributes.1` Given the focusable thumb of a slider, then it MUST have `role="slider"` with `aria-valuenow` set to a decimal representing the current value; axe makes `aria-valuenow` a REQUIRED attribute, so omitting it fails at critical impact. [apg, axe, radix, zag, reka, melt, bits]
- [ ] `slider.roles-and-attributes.2` Given a slider, then `aria-valuemin` and `aria-valuemax` MUST be decimals bounding the value, and they only need to be set when the range differs from the role defaults of 0 and 100; axe allows but does not require them because they are implicit. [apg, axe]
- [ ] `slider.roles-and-attributes.3` Given a slider whose `aria-valuenow` is not user-friendly, for example a numeric day of the week, then `aria-valuetext` MUST be set to a human-readable string; once it is set, assistive technology stops reporting `aria-valuenow`, so it MUST only be used where the bare number is insufficient. [apg]
- [ ] `slider.roles-and-attributes.4` Given a slider with a visible label, then that label MUST be referenced by `aria-labelledby` on the slider element, otherwise `aria-label` MUST supply the name; axe requires a name from `aria-label`, `aria-labelledby` or `title`, does not accept visible text content, and flags a mismatch with a wrapping `label`, at serious impact. [apg, axe, react-aria, base-ui, zag]
- [ ] `slider.roles-and-attributes.5` Given a vertical slider, then it MUST have `aria-orientation="vertical"`; `horizontal` is the role default, and the root, control and value parts carry a matching `data-orientation`. [apg, react-aria, base-ui, zag, bits]
- [ ] `slider.roles-and-attributes.6` Given `role="slider"` in the axe role table, then its role-specific allowed attributes are `aria-valuemax`, `aria-valuemin`, `aria-orientation`, `aria-readonly`, `aria-required` and `aria-valuetext`, its superclasses are `input` and `range`, a name is required, children are presentational, and it MUST NOT contain a focusable widget-role descendant. [axe, apg]
- [ ] `slider.roles-and-attributes.7` Given a slider drawn in SVG, then the wrapping `svg` MUST carry `role="none"` and the decorative rail and range elements MUST carry `aria-hidden="true"`, with `role="slider"` on the element representing the thumb; a decorative `svg` inside a `div` thumb MUST also be `aria-hidden="true"`. A presentational element MUST NOT also carry a `tabindex` or a global ARIA attribute. [apg, axe]
- [ ] `slider.roles-and-attributes.8` Given a set of related sliders such as RGB channels, then they SHOULD be wrapped in `role="group"` with `aria-labelledby`, and each slider keeps its own `aria-labelledby`. [apg]
- [ ] `slider.roles-and-attributes.9` Given a slider wrapper, then it is `role="group"` carrying the slider's accessible name, so the group name and the thumb name are separate. [react-aria, base-ui]
- [ ] `slider.roles-and-attributes.10` Given a multi-thumb slider, then each thumb's `aria-labelledby` composes its own label id with the group's, and where thumbs have no visible label of their own each MUST carry a non-empty `aria-label`, localized where the library ships translations ("Minimum" and "Maximum"). [apg, react-aria, base-ui]
- [ ] `slider.roles-and-attributes.11` Given a thumb-level `aria-label`, `aria-labelledby`, `aria-describedby` or `aria-valuetext` on a thumb wrapper, then the attribute is forwarded onto the inner `role="slider"` element rather than left on the wrapper; a `getAriaLabel` callback replaces the fallback `aria-labelledby` entirely. [base-ui] (candidate)
- [ ] `slider.roles-and-attributes.12` Given a value-output part, then it is an `<output>` with `role="status"` whose `for` lists every thumb id, it joins multiple values with an en dash surrounded by spaces (`40 – 65`, and `40 – 60 – 80 – 95` for four thumbs), and `aria-live="off"` so the thumb announcement is not doubled. [react-aria, base-ui]
- [ ] `slider.roles-and-attributes.13` Given a hidden value-label prop, then the output element is not rendered at all while the thumb keeps its `aria-valuetext`. [react-aria] (candidate)
- [ ] `slider.roles-and-attributes.14` Given the anatomy, then the parts are root, label, control, track, range (indicator), thumb, value text, marker group and markers, plus a dragging indicator; the marker group is `role="presentation"` and `aria-hidden`, and each marker is `role="presentation"` with `data-value` and a `data-state` describing its position relative to the value. [zag, base-ui]
- [ ] `slider.roles-and-attributes.15` Given the root, label, value text, track, range and control parts, then each carries `data-disabled`, `data-orientation`, `data-dragging`, `data-invalid` and `data-focus` so any part can be styled from its own attributes. [zag, base-ui, reka]
- [ ] `slider.roles-and-attributes.16` Given a disabled slider, then the root and every part carry `data-disabled`, and the thumb exposes `aria-disabled="true"` and loses its tab stop. [reka, zag, ark, base-ui, react-aria]
- [ ] `slider.roles-and-attributes.17` Given tick marks derived from the step, then one tick renders per step boundary inclusive of both ends: `min: 0 max: 10 step: 1` gives 11, `max: 8 step: 3` gives 3, `max: 9 step: 3` gives 4, and decimal steps produce clean values (`1`, `1.1`, `1.2`, `1.3`, `1.4`, `1.5`) with no floating-point drift. Changing `min`, `max` or `step` after mount recomputes the count. [melt, bits]
- [ ] `slider.roles-and-attributes.18` Given ticks below or at the current value, then they carry `data-bounded` and the ones above do not; for a range value both thumbs bound the marked span (`[3,6]` with step 3 bounds ticks 1 and 2 but not 0 and 3), and the state updates when the value changes. [melt, bits]
- [ ] `slider.roles-and-attributes.19` Given tick labels, then each carries `data-value`, `data-orientation`, `data-position`, `data-bounded` and `data-selected` on the one matching the current value, its text is the tick's value, and a disabled slider marks every label `data-disabled`; thumb labels carry the same attributes plus `data-active`, and one renders per thumb. [bits] (candidate)
- [ ] `slider.roles-and-attributes.20` Given the thumb wrapper in a nested-input design, then it has no `tabindex` of its own while the inner input has `tabindex="0"`, it carries `data-index`, and a passed child renders alongside the input rather than replacing it. [base-ui] (candidate)
- [ ] `slider.roles-and-attributes.21` Given a slider control, then it has no `tabindex` at all: the thumb is the only tab stop. [base-ui] (candidate)
- [ ] `slider.roles-and-attributes.22` Given a `max` that is not greater than `min`, then a development warning says so. [base-ui] (candidate)
- [ ] `slider.roles-and-attributes.23` Divergence: the thumb is the `role="slider"` element itself, a non-native element carrying `tabindex="0"`, `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext` and `aria-orientation`. [apg, radix, zag, reka, melt, bits] (decision needed)
- [ ] `slider.roles-and-attributes.24` Divergence: the thumb wraps a real `input[type="range"]` that carries `min`, `max`, `step`, `value`, the `name` and the role; the visible thumb is a wrapper with no role. This gets native keyboard support and form participation for free, and forces workarounds: no `for` on the label (WebKit bug 172464 misreports a label pointing at a range input) and no `-webkit-appearance: slider-vertical` on vertical sliders (it changes WebKit's horizontal key handling). [react-aria, base-ui] (decision needed)

### Keyboard

- [ ] `slider.keyboard.1` Given focus on a thumb, when Right Arrow or Up Arrow is pressed the value MUST increase by one step, and when Left Arrow or Down Arrow is pressed it MUST decrease by one step. [apg, react-aria, radix, base-ui, zag, ark, reka, melt, bits]
- [ ] `slider.keyboard.2` Given focus on a thumb, when Home is pressed the value MUST be set to the first allowed value and when End is pressed to the last; this is the numeric minimum and maximum, not the visual start and end, so an inverted slider is unaffected. [apg, react-aria, base-ui, zag, reka, melt, bits]
- [ ] `slider.keyboard.3` Given focus on a thumb, when Page Up or Page Down is pressed, then the value MAY change by an amount larger than the arrow step; the APG marks both keys Optional and its own quantity example implements neither. [apg]
- [ ] `slider.keyboard.4` Given Page Up or Page Down, then the value moves by the large step in that direction and clamps at the bound; the large step is preserved even when it lands off the step grid (`largeStep: 5` with `step: 2` from 20 gives 25). [reka, react-aria, base-ui, zag, ark]
- [ ] `slider.keyboard.5` Given Shift held with an arrow key, then the value moves by the large step, clamping at the minimum or maximum. [base-ui, zag, ark]
- [ ] `slider.keyboard.6` Given an explicit large step, then a bare arrow key still moves by the ordinary step, so the large step applies only to its own keys. [zag, ark, base-ui]
- [ ] `slider.keyboard.7` Given Meta, Control or Alt held with an arrow key, then the value still moves exactly one step and never a fraction of one, so modifier keys cannot leave the step grid. [zag] (candidate)
- [ ] `slider.keyboard.8` Given a slider at its maximum, when an increasing key is pressed, then the value MUST stay at the maximum and MUST NOT wrap to the minimum; likewise at the minimum for a decreasing key. [apg, react-aria, base-ui, zag, bits]
- [ ] `slider.keyboard.9` Given a value already at a bound and a key that cannot move it, then no change callback fires, though react-aria still fires its change-end callback with the unchanged value. [base-ui, react-aria]
- [ ] `slider.keyboard.10` Given a fractional step, then stepping is exact: `step: 0.1` from 0 gives 0.1 and from 0.2 gives 0.3, `step: 1e-7` gives 1e-7 then 2e-7 to twelve decimal places, `step: 1.5e-7` gives 1.5e-7, and `aria-valuenow` is formatted to a fixed precision so repeated presses do not accumulate float drift (the APG temperature example asserts the exact string "25.1" from a 0.1 step). [apg, radix, base-ui, bits]
- [ ] `slider.keyboard.11` Given a value off the step grid, then an arrow key snaps to the next aligned value in that direction rather than skipping a step: 49000 with `min: 1000 step: 5000` goes to 51000 then 56000 going up and 46000 going down, and 5.4698 with `step: 1` goes to 6. [radix, base-ui]
- [ ] `slider.keyboard.12` Given a step whose grid is anchored on `min`, then `min` itself is a valid value and stepping walks the grid from there; with `min: 0 max: 100 step: 30`, four increments stop at 90 and do not overshoot to the maximum. [melt, base-ui]
- [ ] `slider.keyboard.13` Given a key the slider handles, then the handler MUST call `preventDefault` and `stopPropagation`, and MUST NOT do so for keys it does not handle. [apg]
- [ ] `slider.keyboard.14` Given a consumer key handler on the thumb, then it is called exactly once for keys the slider handles (ArrowRight, PageUp) as well as for keys it does not (Enter), and calling `preventDefault` in it suppresses the internal step. [base-ui] (candidate)
- [ ] `slider.keyboard.15` Given a multi-thumb slider, then only the focused thumb's value changes, and each thumb is bounded by its neighbors: End on a lower thumb rises only to the next thumb's value and Home on an upper thumb falls only to the previous thumb's value, not to the absolute bound. [apg, react-aria, base-ui, zag, ark, melt, bits]
- [ ] `slider.keyboard.16` Given a minimum gap between thumbs, then a key press that would close the gap does nothing and fires no callback (`step: 2` with a two-step minimum gap blocks the second press), and the gap is honored when a thumb is pushed toward its neighbor. [radix, base-ui]
- [ ] `slider.keyboard.17` Given a held Page or arrow key producing repeat keydown events, then each repeat applies one step (three PageUp repeats at a page size of 10 move 20 to 50). [react-aria] (candidate)
- [ ] `slider.keyboard.18` Given more thumb elements than values, then a key press on the extra thumb fires no change and no commit, so no `NaN` is committed. [base-ui] (candidate)
- [ ] `slider.keyboard.19` Given a slider inside an open shadow root, then a bubbling keydown on the inner input still steps the value, so key handling works across the shadow boundary. [base-ui] (candidate)
- [ ] `slider.keyboard.20` Divergence: the page size is an explicit `largeStep` prop defaulting to 10 (ten times the step). [reka, zag, ark, base-ui] (decision needed)
- [ ] `slider.keyboard.21` Divergence: the page size is computed as one tenth of the range and then snapped to a multiple of the step, never falling below one step: 0..230 with `step: 10` gives 20, 50..75 with `step: 2` gives 2, and -50..-15 with `step: 2` gives 4. [react-aria] (decision needed)

### Pointer

- [ ] `slider.pointer.1` Given a click on the track away from the thumb, then the nearest thumb MUST jump to the clicked position and MUST receive focus; with thumbs stacked at the same value, a press before them moves the lower-index thumb and a press after them moves the higher-index one. [apg, react-aria, base-ui, zag]
- [ ] `slider.pointer.2` Given a press on the thumb itself, then the value does not jump; the press starts a drag and focuses the thumb. [base-ui, react-aria]
- [ ] `slider.pointer.3` Given a drag in progress, then the value MUST be recomputed from the pointer coordinate along the rail and clamped to the range, with the change callback firing on every move. [apg, react-aria, base-ui, zag, reka]
- [ ] `slider.pointer.4` Given a drag in progress, then `pointermove` and `pointerup` MUST be listened for on the document so a drag that leaves the control still tracks and still terminates. [apg, react-aria, base-ui]
- [ ] `slider.pointer.5` Given a drag that ends, then the commit callback fires exactly once with the final value, and it does not fire again on a later blur; a press and release at the same position with no movement commits nothing. [react-aria, base-ui, radix, reka]
- [ ] `slider.pointer.6` Given a vertical slider, then the value MUST be computed from the pointer Y coordinate with the axis inverted, so a higher position is a higher value. [apg, react-aria, base-ui]
- [ ] `slider.pointer.7` Given a disabled slider, then pressing, dragging or releasing on the track or the thumb changes nothing, fires no callback, and never focuses the thumb; disabling a slider whose thumb has focus blurs it explicitly. [react-aria, base-ui, reka, bits]
- [ ] `slider.pointer.8` Given a disabled individual thumb, then its input is disabled, dragging it does nothing, and a track press nearest to it moves an enabled thumb instead. [base-ui] (candidate)
- [ ] `slider.pointer.9` Given a non-primary pointer button (the right button), then no value change occurs. [base-ui] (candidate)
- [ ] `slider.pointer.10` Given a slider being dragged by one touch point, then a second touch that starts, moves and ends elsewhere is ignored, and the original touch keeps updating the value: a slider tracks only its first touch identifier. [react-aria, base-ui]
- [ ] `slider.pointer.11` Given a touch interaction, then `data-dragging` is only set once the movement looks like a drag rather than a tap: base-ui requires three touchmove events before setting it, and clears it on touchend. [base-ui] (candidate)
- [ ] `slider.pointer.12` Given a repeated pointer position, then the change callback still fires per move event (two moves at the same coordinate fire twice), so the implementation does not dedupe by coordinate. [base-ui] (candidate)
- [ ] `slider.pointer.13` Given a pointermove with no buttons held, then it is ignored, so a drag that lost its button does not keep updating. [base-ui] (candidate)
- [ ] `slider.pointer.14` Given pointer capture on the control, then it is set on pointerdown and released on pointerup, which is what keeps a drag alive outside the element. [base-ui] (candidate)
- [ ] `slider.pointer.15` Given a press on a non-thumb child inside the control, such as a track label, then the press still moves the value. [base-ui] (candidate)
- [ ] `slider.pointer.16` Given the APG slider examples, then they register Pointer Events only and no touch-specific listeners, so touch support comes from pointer event coalescing. [apg]
- [ ] `slider.pointer.17` Given a slider with discrete hit targets, as in the APG rating example, then pointer interaction MAY read a quantized `data-value` off the hit target rather than interpolating a coordinate, and focus is set on click and pointerup rather than on pointerdown. [apg]
- [ ] `slider.pointer.18` Given an inset (edge-aligned) track, then the usable range is inset by half a thumb at each end: a press in the left inset region gives the minimum, the right inset region gives the maximum, and pointer geometry must subtract the thumb size rather than using the raw control box. [base-ui, zag]
- [ ] `slider.pointer.19` Given a range slider whose upper thumb completely covers the lower one at the maximum, then a press at that position and a drag downward moves the LOWER thumb, so a stacked pair stays operable. [base-ui] (candidate) (browser-only)
- [ ] `slider.pointer.20` Divergence: dragging a thumb past its neighbor clamps it at the neighbor's value; the thumbs may become equal but MUST NOT cross, and the tab order MUST stay constant regardless of value. [apg, react-aria, zag, ark] (decision needed)
- [ ] `slider.pointer.21` Divergence: dragging a thumb past its neighbor swaps them, with the dragged thumb continuing past and focus following it to its new index; a `preserveThumbOrder` or `thumbCollisionBehavior` prop selects clamping (`none`), pushing the neighbor along (`push`) or swapping (`swap`). [radix, base-ui, melt, bits] (decision needed)

### Focus management

- [ ] `slider.focus-management.1` Given a slider, then focus MUST be placed on the thumb, that is on the object a pointer user would drag, not on the rail or a wrapper, and the thumb MUST be a stop in the page tab sequence with `tabindex="0"`; a slider is not a composite widget and does not use roving tabindex. [apg, react-aria, base-ui, zag]
- [ ] `slider.focus-management.2` Given a multi-thumb slider, then each thumb is its own tab stop and Tab walks them in DOM order, with Shift+Tab walking back; a `role="group"` wrapper groups them semantically without reducing the number of tab stops. [apg, react-aria, base-ui]
- [ ] `slider.focus-management.3` Given a press on the thumb or the track, then the thumb MUST receive DOM focus as part of the same gesture, so pointer and keyboard interaction stay consistent. [apg, react-aria, base-ui, zag]
- [ ] `slider.focus-management.4` Given a disabled slider between two focusable controls, then Tab skips it entirely. [react-aria, base-ui]
- [ ] `slider.focus-management.5` Given a slider label that is clicked, then the first thumb receives focus; a range slider with per-thumb labels focuses nothing, because there is no single obvious target. [react-aria, base-ui]
- [ ] `slider.focus-management.6` Given two thumbs stacked at the same value, then the focused thumb paints above its sibling (an explicit `z-index`), and the last-used thumb keeps the higher stacking order after focus leaves; with no interaction yet, painting order falls back to DOM order. [base-ui, zag]
- [ ] `slider.focus-management.7` Given a pointer press that focuses the thumb, then `:focus-visible` does not match; a following keydown makes it match, so the focus ring only appears for keyboard use. [base-ui] (candidate)
- [ ] `slider.focus-management.8` Given a thumb with `tabindex="-1"`, then the inner input carries it and Tab skips the slider. [base-ui] (candidate)
- [ ] `slider.focus-management.9` Given an input ref exposed on the thumb, then it points at the inner `role="slider"` input and calling focus on it works. [base-ui, react-aria]
- [ ] `slider.focus-management.10` Given focus and blur handlers on the thumb, then each fires once per transition and `event.currentTarget` is the inner input, not the wrapper. [base-ui] (candidate)

### State

- [ ] `slider.state.1` Given a value change from any source, then `aria-valuenow` MUST be updated and every dependent visible display MUST be updated in the same synchronous step; the APG colour-viewer test asserts the rgb text input, the hex text input and the swatch background all match after each key press. [apg]
- [ ] `slider.state.2` Given a value or default value outside the range, then it is clamped into the range and snapped to the step grid before first paint (default 20 with `max: 10` and `step: 3` renders 9, and `[19, 41]` with bounds 20..40 renders 20 and 40). [react-aria, base-ui, melt]
- [ ] `slider.state.3` Given a controlled value, then the parent stays authoritative: an external write repositions the thumbs, an over-range external write clamps, and a reset restores the parent's values. [react-aria, base-ui]
- [ ] `slider.state.4` Given a change callback, then it fires once per value change with the full value (an array for a multi-thumb slider) and details naming the active thumb index and the reason (`input-change`, `keyboard`, pointer press); the commit callback fires only at the end of an interaction. [react-aria, base-ui]
- [ ] `slider.state.5` Given a change callback that cancels the change, then the value does not move, `aria-valuenow` is unchanged and nothing commits; a cancel armed before a drag release commits nothing either. [base-ui] (candidate)
- [ ] `slider.state.6` Given a value set to the value it already has, then neither callback fires. [react-aria, base-ui]
- [ ] `slider.state.7` Given a dragging thumb, then the change callback fires on every value change while the commit callback fires only when the drag ends, and a per-thumb dragging flag reports the state (exposed as `data-dragging` on the thumb). [react-aria, base-ui]
- [ ] `slider.state.8` Given a multi-thumb slider, then per-thumb bounds are derived from neighbors: each thumb's minimum is the previous thumb's value and its maximum is the next thumb's value, and moving one thumb updates its neighbors' bounds. A neighbor whose value is exactly 0 still bounds its sibling rather than being treated as absent. [apg, react-aria, base-ui]
- [ ] `slider.state.9` Given a step grid with a non-aligned range, then initial values snap to the grid (`min: 1 max: 15 step: 2.5` with `[1, 13]` becomes `[1, 13.5]`), and later writes snap while respecting neighbor bounds, including collapsing two thumbs onto the same value. [react-aria, base-ui]
- [ ] `slider.state.10` Given a value array supplied unsorted or frozen, then the component sorts it into ascending order and never mutates the caller's array. [base-ui] (candidate)
- [ ] `slider.state.11` Given a controlled range whose thumb count changes mid-drag, then the live value wins over the stale one: shrinking to fewer thumbs stops treating it as a range and growing to more picks up the new thumb without throwing. [base-ui] (candidate)
- [ ] `slider.state.12` Given a percentage accessor, then a thumb reports its percent position across the min-to-max range and a value label formatter renders the localized string (`$50.00` for 50 with a USD formatter). [react-aria] (candidate)
- [ ] `slider.state.13` Given the APG rating slider, then decreasing keys floor at `valuemin + 1` while Home alone reaches the true minimum, because the example treats "no rating" as reachable only by reset. [apg]
- [ ] `slider.state.14` Given a slider whose `aria-valuetext` includes a total or a scale description, then the APG examples use a terse form while the slider has focus and a verbose form on blur, so a conformance test MUST capture value text at a defined focus state. The media seek example reads minutes and seconds with singular forms at one, the minutes segment omitted when zero, and "0 Seconds" at zero. [apg]
- [ ] `slider.state.15` Divergence: `aria-valuetext` is always present, carrying the formatted number even with no format options (`"0"`, `"+10"`, `"20%"`). [react-aria, zag] (decision needed)
- [ ] `slider.state.16` Divergence: `aria-valuetext` is absent unless a format is supplied, and for a range slider the default is positional (`"44 start range"`, `"50 end range"`). [base-ui] (decision needed)

### Forms

- [ ] `slider.forms.1` Given a `name`, then each thumb contributes its raw unformatted value to the submission through a hidden input, indexed for multi-thumb sliders (`slider[0]`, or repeated entries under one name), while the visible output shows the formatted string. [reka, radix, base-ui, react-aria, zag]
- [ ] `slider.forms.2` Given a `form` attribute naming an external form, then the value is submitted with and reset by that form rather than an ancestor one. [radix, base-ui, react-aria]
- [ ] `slider.forms.3` Given a form reset, then the value returns to its default in both controlled and uncontrolled mode. [radix, react-aria]
- [ ] `slider.forms.4` Given a submitted value outside the range, then the clamped value is submitted, not the raw one. [base-ui] (candidate)
- [ ] `slider.forms.5` Given a field wrapper, then the slider inherits the field's `name` and `disabled`, gains `data-touched` after focus and blur, gains `data-dirty` on the first change (and loses it when the value returns to its initial state), and gains `data-focused` while focused. [base-ui] (candidate)
- [ ] `slider.forms.6` Given a field validate function, then it receives the numeric value (an array for multi-thumb), runs in the configured mode, and on submit failure focus moves to the `role="slider"` input; in on-blur mode Tab between two thumbs of the same slider does NOT validate, and only focus leaving the slider does. [base-ui] (candidate)
- [ ] `slider.forms.7` Given server validation errors supplied to the form, then the input is `aria-invalid` and described by the error, and editing clears it. [base-ui] (candidate)
- [ ] `slider.forms.8` Given `input[type="range"]`, then its default minimum is 0, its default maximum is 100, its step scale factor is 1 and its default step is 1; a value that is not a valid floating-point number MUST be set to the default value, which is the minimum plus half the range (or the minimum when the maximum is below it). [html]
- [ ] `slider.forms.9` Given a range control suffering underflow or overflow, then the user agent MUST set the value to the minimum or the maximum respectively, so a range clamps rather than merely flagging, unlike `type="number"`; a step mismatch MUST be rounded to the nearest aligned value in the range, preferring the one nearest positive infinity on a tie; and there MUST be no way to set the value to the empty string, so a headless slider has no empty state to model. [html]
- [ ] `slider.forms.10` Given a step mismatch, then it exists when the element has an allowed value step and the value minus the step base is not an integral multiple of that step; `step="any"` means there is no allowed step and the mismatch can never apply. [html]
- [ ] `slider.forms.11` Given a headless slider that participates in forms, then the shared form-association, constraint-validation and disabled-element rules in `number-field.forms.14` through `number-field.forms.20` apply unchanged. [html]

### Positioning

- [ ] `slider.positioning.1` Given a value, then the thumb is positioned as a percentage of the track (30 of 0..100 gives 30%, 0.5 of 0..1 gives 50%, 0 of -50..50 gives 50%), and the filled range spans from the track start to the thumb (`left: 0%`, `right: 70%` at 30). [melt, bits, base-ui]
- [ ] `slider.positioning.2` Given a two-thumb slider, then each thumb sits at its own percentage and the filled range spans between them (`left: 20%`, `right: 20%` for `[20, 80]`). [melt, bits, base-ui]
- [ ] `slider.positioning.3` Given a fill with an offset origin, then it spans from the value to the offset when the value is below it and from the offset to the value when above (offset 50 with value 30 gives start 30% width 20%, with value 80 gives start 50% width 30%), and the vertical case uses `bottom` and `height` instead of `insetInlineStart` and `width`. [react-aria] (candidate)
- [ ] `slider.positioning.4` Given positioning custom properties, then the root exposes a per-thumb offset plus thumb width, height and transform and the range start and end, so the range positions itself from two variables and each thumb from its own; the thumb transform is `translateY(50%)` vertically, `translateX(50%)` in RTL and `translateX(-50%)` otherwise, and markers center over their value with mirrored translations. [zag] (candidate)
- [ ] `slider.positioning.5` Given tick and thumb labels with a position prop, then each label carries `data-position` and the matching inset (`bottom` giving `top: 100%`). [bits] (candidate)
- [ ] `slider.positioning.6` Given percentage assertions on computed styles, then equality MUST be checked within a tolerance (melt and bits use 0.0001) because floating-point arithmetic leaks into the style string. [melt, bits]

### Animation and presence

- [ ] `slider.rtl-and-i18n.3` Given a vertical slider, then Up and Right both increase and Down and Left both decrease; the APG examples do not remap axes for vertical orientation, and every library keeps both axes live on a vertical slider. [apg, react-aria, base-ui, reka, ark]
- [ ] `slider.rtl-and-i18n.4` Given an inverted slider, then the horizontal arrows swap direction while the vertical arrows do not, and in a vertical inverted slider the vertical arrows swap while the horizontal ones do not; Home and End keep pointing at the numeric minimum and maximum. [reka] (candidate)
- [ ] `slider.rtl-and-i18n.5` Given format options, then the value output and `aria-valuetext` are both formatted with them (currency, percent, fixed fraction digits), and changing the options recomputes the rendered text at the same value. [react-aria, base-ui]
- [ ] `slider.rtl-and-i18n.6` Given a locale prop or provider, then the formatted value uses that locale's separators (a `de-DE` two-fraction-digit decimal renders with a comma), and a range joins the two localized numbers. [base-ui] (candidate)
- [ ] `slider.rtl-and-i18n.7` Given a range that crosses zero, then the formatted value carries an explicit plus sign above zero (`+10`, and `+10 – +20` for a range) and drops it at and below zero. [react-aria] (candidate)

### Notes and edge cases

- [ ] `slider.notes-and-edge-cases.1` Given the APG page-step conventions, then the big step is chosen per widget: 15 of 300 for the media seek slider, 2.0 against a 0.1 arrow step for the temperature slider, 2 of 10 for the rating slider, and 10 of 255 for each colour channel. [apg]
- [ ] `slider.notes-and-edge-cases.2` Given a multi-thumb slider, then there is no enforced minimum gap unless one is configured: thumbs can converge on the same value. [apg]
- [ ] `slider.notes-and-edge-cases.3` Given unconsumed props on the root, track, range, thumb or hidden input, then they land on the rendered element and the ref resolves to it; library-owned inline positioning is merged with the author's `style` rather than replacing it, and a composed ref keeps a stable identity across re-renders. [radix, base-ui]
- [ ] `slider.notes-and-edge-cases.4` Given `asChild` or `render` onto another tag, then that tag renders and still carries the part's role and attributes (`role="slider"` with `aria-valuenow` on a thumb, `data-orientation` on the root and track), and a render prop that discards the forwarded ref degrades to an inert control rather than throwing. [radix, base-ui]
- [ ] `slider.notes-and-edge-cases.5` Given a part rendered with no slider root ancestor, then it throws a named context error. [base-ui] (candidate)
- [ ] `slider.notes-and-edge-cases.6` Given the step rounding helper, then it preserves the decimal precision implied by the step origin: `roundValueToStep(0.35, 0.1, 0.25)` returns exactly 0.35 and `roundValueToStep(13.2, 1.5, 10.2)` returns exactly 13.2. [base-ui] (candidate)
- [ ] `slider.notes-and-edge-cases.7` Given the thumb-collision helpers, then their contract is testable directly: `none` clamps the pressed thumb at its neighbor, `push` moves the neighbor along and restores it toward its initial value when the pressed thumb comes back, and `swap` exchanges places and returns the new thumb index so the caller can follow focus. A swap fires when the pressed thumb reaches exactly the neighbor's value, not before; a fractional minimum gap produces exact values with no float drift; and a live value array that changed mid-interaction wins over the stale one, including collapsing a range to a scalar. [base-ui] (candidate)
- [ ] `slider.notes-and-edge-cases.8` Given a conformance harness for a slider, then it needs per-thumb locators by index, the control, track and value-text parts, a geometry helper that maps a 0-1 percentage to a page point by measuring the control and thumb boxes, insetting by half a thumb for edge alignment and inverting the axis for vertical sliders, plus press-and-move helpers that do not release. [zag] (candidate)
- [ ] `slider.notes-and-edge-cases.9` Given jsdom, then `ResizeObserver`, `scrollIntoView`, `hasPointerCapture`, `setPointerCapture` and `releasePointerCapture` must be stubbed for any pointer math to run at all (jsdom/jsdom#2666), and element rects must be mocked; a slider's pointer contract can only be asserted honestly in a browser-mode suite. [reka, radix, base-ui]
- [ ] `slider.notes-and-edge-cases.10` Given ark's slider tests, then they read thumbs with `getAllByRole('slider', { hidden: true })` because the thumbs sit in a container testing-library treats as hidden until measured, and ark's Vue suite keeps the RTL, vertical, disabled, thumb-overlap and change-callback cases commented out, so Vue is only proven for LTR horizontal keyboard stepping. [ark] (candidate)
- [ ] `slider.notes-and-edge-cases.11` Given reka's slider, then the drag-lifecycle event tests (slide start, slide move, slide end) are skipped, so only the committed value is actually verified. [reka] (candidate)
- [ ] `slider.notes-and-edge-cases.12` Given a stray global `event` object whose constructor throws, then a change event on a controlled slider still reports normally rather than throwing, so the implementation MUST NOT read `globalThis.event`. [base-ui] (candidate)

## Deferred

- Native input versus a `role="slider"` div (`slider.roles-and-attributes.23` and `.24`). The first decision to make. A nested `input[type="range"]` brings native keyboard handling, native form participation and native validation, at the cost of two WebKit workarounds (no `for` on the label, no `slider-vertical` appearance) and a wrapper element with no role. A plain div needs every key and the form value implemented by hand. Both camps are large; the choice shapes every other subsection.
- Thumb collision (`slider.pointer.20` and `.21`). Clamp at the neighbor, or swap. The APG says thumbs must not cross and the tab order must stay constant; radix, base-ui, melt and bits swap by default and move focus with the dragged thumb. If we swap, `slider.focus-management.2` needs rewording, since the tab order then does follow value order.
- Page size (`slider.keyboard.20` and `.21`). An explicit `largeStep` defaulting to 10, or one tenth of the range snapped to the step. react-aria's rule is better for a 0..1000 slider and worse for a 0..3 one.
- Default `aria-valuetext` (`slider.state.15` and `.16`). Always the formatted number, or absent until a format is given. Setting it suppresses `aria-valuenow` in assistive technology, which argues for base-ui's restraint; always having it argues for consistent announcements.
- angle-slider. zag and ark ship a circular slider (`role="slider"` on a thumb with `aria-valuemin` 0 and `aria-valuemax` 360, `--value` and `--angle` custom properties, arrow keys mapped through a horizontal key lookup, Home and End to the ends, a `role="presentation"` control and a `type="hidden"` input). Its pointer contract is genuinely different: a click jumps to the clicked angle, and a drag started off-center preserves the grab offset for the whole drag instead of snapping the thumb center to the pointer (verified at 0 to 90 degrees and 45 to 180 degrees, within a 10-degree tolerance). No other library has one, so it is one source for a whole component; it gets its own spec file if and when we build it.
- Ticks, tick labels and thumb labels. melt and bits agree on the tick count and `data-bounded` rules, and bits alone specifies labels. The bullets are recorded (`slider.roles-and-attributes.17` through `.19`) but the label parts are a bits-only API, so the shared contract stops at the ticks.
- Inverted orientation (`slider.rtl-and-i18n.4`). Only reka has it, and two of its own test names disagree with what the tests assert. If we add it, the interaction with RTL needs its own bullets.
- Everything in Pointer and Positioning needs measured layout. jsdom cannot do it (`slider.notes-and-edge-cases.9`), so those bullets belong in a browser-mode harness. The suite should assert value changes through the keyboard path wherever it can and reserve pointer geometry for the browser run.
