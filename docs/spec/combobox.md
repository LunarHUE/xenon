# combobox

The editable `role="combobox"` and its popup. A text input that filters a list,
and everything built on it: autocomplete and search fields, the command palette,
async (server-filtered) collections. All four APG autocomplete flavors belong
here. Three of them are specified below (`aria-autocomplete="none"`, `"list"`
and `"both"`); the fourth, the non-editable select-only combobox, is in
`select.md`. The popup's option semantics are in `listbox.md`.

Note: kobalte's combobox suite is `describe.skip` upstream apart from one live
regression test (the filter-then-click case, `combobox.focus-management.11`), so
every other kobalte-tagged bullet here is unverified.

## combobox

### Roles and attributes

- [ ] `combobox.roles-and-attributes.1` Given the element that serves as an input and displays the combobox value, then it has `role="combobox"`. [apg, react-aria, base-ui, zag, ark, kobalte, reka, ariakit, headlessui]
- [ ] `combobox.roles-and-attributes.2` Given a combobox, then `aria-autocomplete` matches its behavior: `none` when the suggestions do not vary with the typed characters, `list` when the popup presents suggestions for the typed characters, `both` when it does that and also shows an inline completion after the cursor. [apg, react-aria, base-ui, zag, kobalte]
- [ ] `combobox.roles-and-attributes.4` Given a combobox popup, then it has `role="listbox"`, `role="tree"`, `role="grid"` or `role="dialog"`. [apg, base-ui, ariakit]
- [ ] `combobox.roles-and-attributes.5` Given a popup with a role other than `listbox`, then the combobox has `aria-haspopup` set to `grid`, `tree` or `dialog` to match; `role="combobox"` carries an implicit `aria-haspopup="listbox"` that implementations also write explicitly. [apg, react-aria, base-ui, zag, kobalte]
- [ ] `combobox.roles-and-attributes.8` Given a hidden combobox popup, then the combobox has `aria-expanded="false"`; while the popup is visible, `aria-expanded="true"`. `combobox` defaults to `false`. [apg, react-aria, base-ui, zag, kobalte, ariakit]
- [ ] `combobox.roles-and-attributes.9` Given a combobox, then `aria-expanded` is kept in sync on both the combobox element and the separate open button, if one exists. [apg, react-aria]
- [ ] `combobox.roles-and-attributes.10` Given a combobox, then `aria-controls` refers to the popup element; it only needs to be set while the popup is visible, though referencing a hidden element is also valid. `aria-owns` is not used for this. [apg]
- [ ] `combobox.roles-and-attributes.11` Divergence: given a closed combobox, then `aria-controls` is absent entirely and appears (pointing at the listbox id) only while the popup is open. [apg, react-aria, base-ui, zag, kobalte] (decision needed)
- [ ] `combobox.roles-and-attributes.12` Divergence: given `role="combobox"`, then both `aria-expanded` and `aria-controls` are required attributes, so a closed combobox with no `aria-controls` fails at critical impact regardless of popup visibility. [axe] (decision needed)
- [ ] `combobox.roles-and-attributes.13` Given `aria-controls` on a combobox that also carries `aria-haspopup`, then an unresolvable reference is reported incomplete ("Unable to determine if aria-controls referenced ID exists on the page while using aria-haspopup") rather than failing, so a lazily rendered popup surfaces as needing review. [axe]
- [ ] `combobox.roles-and-attributes.14` Given a combobox before any interaction, then `aria-activedescendant` is absent. [apg, react-aria, base-ui, zag, kobalte]
- [ ] `combobox.roles-and-attributes.15` Divergence: given a combobox whose popup has been opened and dismissed, then `aria-activedescendant` is set to the empty string rather than removed; axe reports an empty value as incomplete ("ARIA attribute value is ignored while empty"). [apg, axe] (decision needed)
- [ ] `combobox.roles-and-attributes.16` Divergence: given no highlighted option, then `aria-activedescendant` is removed from the input entirely. [react-aria, base-ui, zag, ariakit] (decision needed)
- [ ] `combobox.roles-and-attributes.17` Given a focused descendant of a listbox, grid or tree popup, then DOM focus stays on the combobox and `aria-activedescendant` refers to that element. [apg, react-aria, base-ui, zag, kobalte, ariakit]
- [ ] `combobox.roles-and-attributes.18` Given a suggested value that is visually indicated as selected, then the containing `option`, `gridcell`, `row` or `treeitem` has `aria-selected="true"`. [apg, react-aria, base-ui, zag, kobalte, reka, ariakit, bits]
- [ ] `combobox.roles-and-attributes.19` Divergence: given an editable combobox with a listbox popup, then `aria-selected` is removed from non-matching options rather than set to `"false"`; bits likewise leaves unselected options with neither `aria-selected` nor the selected data attribute. [apg, bits] (decision needed)
- [ ] `combobox.roles-and-attributes.20` Divergence: given an unselected option, then it carries `aria-selected="false"` explicitly. [base-ui, zag, kobalte, ariakit] (decision needed)
- [ ] `combobox.roles-and-attributes.21` Given a combobox popup, then at most one suggestion is selected at a time in single-selection mode, because selection follows focus in the popup. [apg]
- [ ] `combobox.roles-and-attributes.23` Given a combobox that is a labelable element such as an `input` with a visible label, then it is labelled with a `label` element; otherwise `aria-labelledby` references the visible label; otherwise `aria-label` supplies the name. [apg, axe, react-aria, base-ui, kobalte]
- [ ] `combobox.roles-and-attributes.31` Given a combobox with a graphical open button, then that button has `tabindex="-1"`, its own accessible name from `aria-label`, `aria-controls` pointing at the popup, and `aria-expanded` mirroring the combobox's state. [apg, zag, kobalte]
- [ ] `combobox.roles-and-attributes.54` Given `role="combobox"` in the axe role table, then it is a widget-type role whose role-specific allowed attributes are `aria-owns`, `aria-autocomplete`, `aria-readonly`, `aria-required`, `aria-activedescendant` and `aria-orientation`, its superclass is `select`, a name is required, and its children are not presentational. [axe]
- [ ] `combobox.roles-and-attributes.6` Given a combobox whose input lives inside the popup, then the popup is a `dialog` (the trigger reports `aria-haspopup="dialog"`) and the outer trigger, not the input, owns the combobox role, id and `aria-controls`. [base-ui, zag, ariakit]
- [ ] `combobox.roles-and-attributes.22` Given a multiple-selection combobox, then the listbox carries `aria-multiselectable="true"`. [react-aria, base-ui, kobalte, zag]
- [ ] `combobox.roles-and-attributes.24` Given a combobox with a label part, then the input's `aria-labelledby` is just the label's id, with no value element folded in (unlike a select trigger, which composes label plus value). [kobalte, react-aria]
- [ ] `combobox.roles-and-attributes.28` Given an open combobox, then the listbox is labelled by the field's label; react-aria and kobalte compose it as "<listbox id> <label id>" so the popup also names itself, and react-aria adds `aria-label="Suggestions"`. [react-aria, kobalte, zag]
- [ ] `combobox.roles-and-attributes.29` Given a description or error-message part, then it has an id and the input's `aria-describedby` points at it; a field-level description id is appended to an author-supplied `aria-describedby` rather than replacing it. [react-aria, base-ui, kobalte]
- [ ] `combobox.roles-and-attributes.32` Given a combobox with both an input and a trigger, then the trigger stays `tabindex="-1"` (the input is the tab stop) and gains no `role` or `aria-required`/`aria-readonly` of its own; with no input outside the popup, the trigger becomes the anchor with `tabindex="0"`, `role="combobox"` and those attributes. [base-ui, zag, kobalte]
- [ ] `combobox.roles-and-attributes.33` Given a required combobox, then the input carries `aria-required="true"`. [base-ui, zag]
- [ ] `combobox.roles-and-attributes.34` Given a disabled combobox, then the input and the trigger both carry the native `disabled` attribute, inherited from the root or a field wrapper, with a local prop winning over the root. [base-ui, zag, ark, kobalte, headlessui]
- [ ] `combobox.roles-and-attributes.35` Given a combobox input, then it carries `autocomplete="off"`, `autocorrect="off"` and `spellcheck="false"`, and react-aria and zag add `enterkeyhint="go"`. [react-aria, base-ui, zag]
- [ ] `combobox.roles-and-attributes.38` Given a grid-shaped popup, then the list has `role="grid"`, the cells `role="gridcell"`, and a group becomes `role="rowgroup"` rather than `role="group"`. [base-ui, ariakit]
- [ ] `combobox.roles-and-attributes.39` Given a group in the popup, then it has `role="group"` with `aria-labelledby` pointing at its label element's id; the group label is `aria-hidden="true"` by default (overridable) so it is not announced twice, and a newer label registration wins over an unmounting older one. [base-ui, zag, reka, bits]
- [ ] `combobox.roles-and-attributes.40` Given each option, then it carries a stable id, `tabindex="-1"`, `aria-selected`, a highlighted marker, a checked/unchecked state attribute, `data-value`, and `aria-disabled` plus `data-disabled` when disabled. [base-ui, zag, kobalte, reka, bits, headlessui]
- [ ] `combobox.roles-and-attributes.42` Given an item indicator part, then it is `aria-hidden="true"` and is absent (or `hidden`) unless its option is selected; a kept-mounted indicator loses its selected marker when the option is deselected. [base-ui, zag, reka, bits]
- [ ] `combobox.roles-and-attributes.43` Given a clear trigger, then it is a `button type="button"` with `tabindex="-1"`, a translated `aria-label`, `aria-controls` pointing at the input, and it is `hidden` (or unmounted) whenever the value is empty. [zag, base-ui, react-aria]
- [ ] `combobox.roles-and-attributes.44` Given an empty filtered list, then the container is marked empty (`data-empty`, `data-list-empty` on the input and trigger) and an empty-state part renders with `role="status"`. [base-ui, zag, reka]
- [ ] `combobox.roles-and-attributes.49` Given a combobox rendered on a non-`input` element (a `textarea`, or an `input type="email"`), then no invalid `type` attribute is injected, the element stays editable, and the combobox attributes appear only while the popup is open (immediately, for an inline list). [base-ui, ariakit]
- [ ] `combobox.roles-and-attributes.3` Given a read-only combobox, then `aria-autocomplete` is `none` even in inline-completion mode, and the input carries `aria-readonly="true"` plus the native `readonly` attribute. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.7` Given a combobox whose popup wraps a nested list (a tree, a menu, or an inner listbox that is the real list), then the popup reports `dialog` and the nested list keeps its own role; an unrelated inner listbox, a popup that shares its element with the list, or a second list portaled outside the popup all leave `aria-haspopup="listbox"` in place. [ariakit] (candidate) (chrome-only)
- [ ] `combobox.roles-and-attributes.25` Given an author `aria-labelledby` on the input, then it is used verbatim; with both `aria-label` and `aria-labelledby`, kobalte appends the input's own id to the list. [kobalte] (candidate)
- [ ] `combobox.roles-and-attributes.26` Given a combobox whose input is inside the popup and whose trigger has an explicit id, then the label links to the trigger rather than to the input, and labelling the popup input instead warns on the console ("`<Combobox.Label>` labels `<Combobox.Trigger>` only"). [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.27` Given a label rendered inside the popup and bound to the popup input by `for`, then the popup input takes that name and the outer trigger keeps its own. [ariakit] (candidate) (browser-only)
- [ ] `combobox.roles-and-attributes.30` Given a combobox whose input is inside the popup, then the field's validation attributes (`aria-invalid`, `aria-describedby`, `data-valid`, `data-touched`, `data-dirty`, `data-filled`, `data-focused`) land on the outer trigger and never on the popup input. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.36` Given a listbox popup, then it has no `aria-orientation`; a `grid` popup likewise has none, because the role disallows it. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.37` Given a read-only combobox, then the listbox carries `aria-readonly="true"`, while a `grid` popup does not (there the attribute would describe cell editability). [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.41` Given wrapper elements between the options container and the options, then each intermediate element is given `role="none"` so the required-children rule still passes. [headlessui] (candidate)
- [ ] `combobox.roles-and-attributes.45` Given a status part, then it renders only while the popup is open and is itself the `role="status"` live region. (candidate) [base-ui]
- [ ] `combobox.roles-and-attributes.46` Given a multiple-selection combobox with chips, then the chips container takes `role="toolbar"` only once at least one chip exists, each chip carries `aria-disabled`/`aria-readonly` from the root, and the chip remove button is `tabindex="-1"`. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.47` Given an input group wrapping the input and trigger, then it has `role="group"` and never gains `data-placeholder`. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.48` Given an item that highlights the typed substring, then the item text is split into `data-user-value` spans for the typed characters and `data-autocomplete-value` spans for the rest; overlapping matches merge into one span rather than duplicating text, and a query that normalizes to empty produces no user-value span at all. [ariakit] (candidate)
- [ ] `combobox.roles-and-attributes.50` Given a combobox rendered inline (a list always present, no popup), then the input already reports `aria-expanded="true"` with `aria-controls` set, and clicking it changes neither. [base-ui] (candidate)
- [ ] `combobox.roles-and-attributes.51` Given an option with no value, or an explicitly unregistered index, then it gets no id and never becomes the active descendant. (candidate) [base-ui]
- [ ] `combobox.roles-and-attributes.52` Given a scrollable popup list, then the list itself carries `tabindex="-1"`, even when empty and even when the author set a different `tabIndex`. [ariakit] (candidate)
- [ ] `combobox.roles-and-attributes.53` Given a combobox whose input id changes at runtime, then the label's `for`, the clear button's `aria-controls` and the input's own id all follow it; the same holds for a label id change and the listbox's `aria-labelledby`. [ariakit] (candidate)
- [ ] `combobox.roles-and-attributes.55` Given the root of a command palette, then the first item is selected by default, an explicit value selects that item instead (including one in a later group or the last item of the first group), and the selected item carries the selected marker. [bits] (candidate)

- [ ] `combobox.notes-and-edge-cases.2` Given list autocomplete with manual selection, then the typed string becomes the combobox value unless the user selects one in the popup; with automatic selection, the auto-selected suggestion becomes the value when the combobox loses focus unless the user chooses another or changes the typed string. List-with-inline autocomplete is automatic selection plus a visible completion string after the cursor. [apg]
- [ ] `combobox.notes-and-edge-cases.3` Given an editable combobox with list autocomplete, then the popup may appear and disappear as the user types: a third character that forms a string with no matches may close it and drop the inline completion. [apg]
- [ ] `combobox.notes-and-edge-cases.4` Given a choice between combobox, listbox and menu button, then combobox and menu button both let the user explore choices and press Escape to back out without changing previous input, whereas navigating a single-select listbox changes its value immediately; combobox and listbox both support `aria-required="true"` and have a name distinct from their value, while a menu button has neither, so a menu button must not convey a choice in its collapsed state. [apg]
- [ ] `combobox.notes-and-edge-cases.5` Given a combobox popup as a popover, then a show action while already showing (or a hide while hidden) is a no-op, and cancelling `beforetoggle` aborts the change, so `aria-expanded` is written from the `toggle` event or after the show resolves rather than optimistically. [html]
- [ ] `combobox.notes-and-edge-cases.6` Given a combobox popup implemented with `popover="auto"`, then it gets light dismiss on an outside `pointerdown`/`pointerup` pair and responds to close requests, matching the APG outside-click and Escape behavior. [html]
- [ ] `combobox.notes-and-edge-cases.9` Given a combobox part rendered without its required ancestor, then the render fails with a message naming the missing context and the part that needs it. [base-ui, headlessui]
- [ ] `combobox.notes-and-edge-cases.18` Given a portaled popup, then the test has to query it from the document body rather than from the render container. [kobalte, reka]
- [ ] `combobox.notes-and-edge-cases.22` Divergence: the primitive does not filter at all: the consumer derives the visible items from the query and owns the empty state and the query reset. [bits] (decision needed)
- [ ] `combobox.notes-and-edge-cases.24` Divergence: the primitive filters internally against its items and owns the empty state. [base-ui, react-aria, reka] (decision needed)
- [ ] `combobox.notes-and-edge-cases.7` Given a combobox that offers a "create" option for the typed query, then activating it fires the item's action rather than a selection change, and the input value is restored to the previously selected item afterwards. [react-aria] (candidate)
- [ ] `combobox.notes-and-edge-cases.8` Given a command palette, then item scoring is exact match 1, case-insensitive near-1, prefix above interior, continuous above skipped, word boundaries above punctuation, keywords counted alongside the item text, transposed characters above 0, no match exactly 0, and an empty query 0.99 against a non-empty item. [bits] (candidate)
- [ ] `combobox.notes-and-edge-cases.10` Given any polymorphic combobox part, then unconsumed props, `className`, inline styles, refs and author event handlers land on the rendered element and compose with the library's own handlers. This holds for the root, input, trigger, popup, positioner, portal, list, item, item indicator, group, group label, label, value, chips, chip, chip remove, clear, empty, status, arrow, backdrop, icon and input group. [base-ui] (candidate)
- [ ] `combobox.notes-and-edge-cases.11` Given a root store publishing several synchronized values, then a prop change lands as one transaction: no subscriber observes a snapshot mixing old and new values, and store commands are already available to a descendant ref callback on the first commit. [base-ui] (candidate)
- [ ] `combobox.notes-and-edge-cases.12` Given a filtering keystroke that leaves the item membership unchanged, then no still-mounted option re-renders. (candidate) [base-ui]
- [ ] `combobox.notes-and-edge-cases.13` Given items that go from an array to undefined, or an items object that is not a collection, then no infinite re-render loop occurs and a non-collection object throws a descriptive error. [base-ui] (candidate)
- [ ] `combobox.notes-and-edge-cases.14` Given duplicate derived values in a collection, then the first occurrence wins for label resolution and the library warns on the console for each duplicate. (candidate) [base-ui]
- [ ] `combobox.notes-and-edge-cases.15` Given a combobox rendered inside a dialog with an error-message slot, or an alert dialog, then it does not throw. (candidate) [react-aria]
- [ ] `combobox.notes-and-edge-cases.16` Given a combobox whose children prop is an inline function (a new identity every render), then rendering settles without an infinite loop and the input keeps its combobox role. (candidate) [react-aria]
- [ ] `combobox.notes-and-edge-cases.17` Given a combobox under a test runner, then the filtered list needs two consecutive microtask flushes plus a timer flush before it is queryable, because the filter runs through its own derived computation before the collection rebuild; the suite needs an explicit settle helper rather than counted microtasks. [kobalte] (candidate)
- [ ] `combobox.notes-and-edge-cases.19` Given a virtual-focus assertion, then "has focus" means following the input's `aria-activedescendant` to the option, not `document.activeElement`; ariakit installs a custom matcher that does this and it is the shape our harness needs. [ariakit] (candidate)
- [ ] `combobox.notes-and-edge-cases.20` Given an assertion that something did not happen (a prevented scroll, a withheld focus, a cancelled presentation), then the test has to cross animation-frame checkpoints, because there is no positive completion state to wait for. [ariakit] (candidate)
- [ ] `combobox.notes-and-edge-cases.21` Given two typeahead sequences that must not merge, then 600 ms between them is enough in ariakit's suites, which pins the reset window from the outside. [ariakit] (candidate)
- [ ] `combobox.notes-and-edge-cases.23` Given reka's `Autocomplete` versus its `Combobox`, then typing writes the model value directly in `Autocomplete`, so closing keeps the typed text instead of snapping back to a selected option's label. [reka] (candidate)

## Deferred

- Grid, tree and dialog popups. APG specifies full keyboard tables for all three, base-ui ships a `grid` mode with rows and `rowgroup`s and uneven-row clamping, and Ariakit has grid comboboxes and nested tree and menu popups. Each needs its own collection harness, and the dialog popup is really the dialog pattern with a combobox anchor. [apg, base-ui, ariakit]
- Virtualized popups: windowed rendering with explicit or derived indexes, `Combobox.useFilteredItems`, `aria-setsize`/`aria-posinset` over the full collection, scroll-to-index on a programmatic highlight, and Ariakit's renderer scroll-target resolution (auto-detection, refs that resolve late, released targets). Shares a harness with `listbox.md`'s virtualization work. [base-ui, reka, ariakit, react-aria]
- Async and server-filtered collections beyond the state contract above: zag's `async-list` machine has no tests of its own, and react-aria's loading-spinner timing, `onLoadMore` and `useAsyncList` integration all need a fake-timer plus network harness. [zag, react-aria]
- The mobile tray. react-aria replaces the input with a trigger button, opens a tray with its own labelled input and dismiss buttons, keeps the tray height fixed as the list filters, blurs the tray input on touch scroll so the keyboard dismisses, and pins several VoiceOver and TalkBack quirks. One library, and it needs a viewport harness. [react-aria]
- Caret-anchored comboboxes (`@`, `#` and `:` triggers inside a textarea): trigger detection, insertion with a trailing space, the popup unmounting when the caret leaves the trigger, and caret-following positioning. Only Ariakit. [ariakit]
- Combobox composed with tabs (a tab bar inside the popup, tab panels as option lists, arrow keys crossing between input, tabs and options, per-tab scroll restoration, animated tab restoration). Only Ariakit, and it needs the tabs spec first. [ariakit]
- Inline completion (`aria-autocomplete="both"`) at the character level: the selected completion range, caret preservation across delayed result updates, NFD/NFC safety, diacritic-insensitive completion, Hangul and kana highlighting. The APG-level contract is specified above; the grapheme-level behavior is a separate piece of work with its own fixtures. [apg, ariakit]
- Drag and drop out of a combobox popup, and reorderable results. No library covers it.
- Command-palette grid mode (two-dimensional arrow navigation across a column count). Only bits, and it shares the grid harness with the deferred grid popup work. [bits]
