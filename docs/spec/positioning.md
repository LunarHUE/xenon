The one cross-cutting spec for anchored positioning. Dialog, drawer, popover,
tooltip, hover card, menu and select point here for side and align resolution,
offsets, collision handling, the arrow, the anchor, the CSS custom properties
and the update triggers, and keep only the bullets that are their own.

The implemented xenon contract is documented in [positioning](../positioning.md).
This checklist retains source observations and alternatives. Revalidation on
2026-09-14 found that `.positioning.15` conflates Zag's width-only matching with
Corvu's axis matching; `.positioning.16` conflates the viewport root boundary
with ignoring clipping ancestors; `.state.2` overstates Zag's callback coverage;
and `.notes.6` overlooks style writes inside Zag's size and arrow middleware.
The malformed transform origins in `.notes.9` and `.notes.10` describe observed
defects, not desired xenon behavior. See the implementation document for the
adopted defaults, source links, and deferred interaction-specific choices.

## positioning

### Roles and attributes

- [ ] `positioning.roles.1` Given popper content with an arrow, when it mounts, then the positioning styles live on a wrapper element around the content rather than on the content itself, and that wrapper is findable by a library data attribute, `data-radix-popper-content-wrapper` or `data-reka-popper-content-wrapper`. [radix, reka]
- [ ] `positioning.roles.2` Given a positioned element with an arrow part, when the arrow renders, then it is hidden from assistive technology with `aria-hidden="true"` and `role="presentation"`. (candidate) [react-aria]
- [ ] `positioning.roles.3` Given a floating element, when the arrow middleware looks for its arrow, then it finds it by the selector `[data-part=arrow]` inside the floating element. (candidate) [zag]

### Focus management

- [ ] `positioning.focus.1` Given a trigger that captured pointer coordinates while closed, when the popup is instead opened by a non-pointer reason such as trigger focus, then the anchor rect reverts to the trigger's own DOM rect (`x: 10, y: 20, width: 30, height: 40`), later `mousemove` events on the body or the trigger leave that rect unchanged, and a `focus` handler clears any stored inline-rect coordinates. (candidate) [base-ui]

### State

- [ ] `positioning.state.1` Given a positioned element that has not yet been measured, when its state is read, then `placement` is the requested placement, `x` and `y` are `0`, and `width`, `height`, `maxWidth`, `maxHeight`, `arrowX` and `arrowY` are all `null` rather than stale or guessed values. (candidate) [corvu]
- [ ] `positioning.state.2` Given a positioned element with an `onPositioned` callback, when a position lands, then it fires with `placed: true`, and when the positioner is torn down it fires with `placed: false`, so a consumer can tell a positioned element from a dismantled one. (candidate) [zag]

### Dismissal and layering

- [ ] `positioning.dismissal.1` Given an open positioned overlay, when an ancestor scroll container, `document.body`, `document` or `window` fires `scroll`, then `onClose` is called once, and when an adjacent sibling scrollable region scrolls, then `onClose` is not called. (candidate) [react-aria]
- [ ] `positioning.dismissal.2` Given a positioned overlay, when it is placed, then it gets `z-index: 100000` inline. (candidate) [react-aria]
- [ ] `positioning.dismissal.3` Given a floating element, when it is placed, then it gets `isolation: isolate` and `z-index: var(--z-index)`, where `--z-index` is copied from the computed `z-index` of its first element child and read once per floating node so position updates do not force a reflow. (candidate) [zag]

### Positioning

- [ ] `positioning.positioning.1` Given a placement value, when it is validated, then the accepted forms are `top`, `bottom`, `left` and `right`, each optionally suffixed with `-start` or `-end`, split into `{ side, align, hasAlign }`; react-aria spells the same thing as a side plus a cross-axis word, such as `bottom left` or `right top`. [react-aria, zag]
- [ ] `positioning.positioning.2` Given no explicit placement, when the element is positioned, then the side is `bottom` and the align is `center`. [radix, zag, corvu, reka]
- [ ] `positioning.positioning.3` Given a 100 by 100 target at (250,250), a 200 by 200 overlay, a 600 by 600 boundary, collision padding 50 and arrow size 8, when position is calculated for each side, then the overlay's top left corner lands at (200,350) for `bottom`, (200,50) for `top`, (50,200) for `left` and (350,200) for `right`, and `top` and `left` are written as a `bottom` or `right` coordinate rather than a `top` or `left` one so the element grows away from the target. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.4` Given the same fixture on a vertical side, when align is applied, then `bottom left` puts the overlay at (250,350) with the arrow 50px in, `bottom right` at (150,350) with the arrow 150px in, `top left` at (250,50) and `top right` at (150,50), so the aligned overlay edge lines up with the same target edge and the arrow offset follows the target center. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.5` Given the same fixture on a horizontal side, when align is applied, then `left top` puts the overlay at (50,250) and `right top` at (350,250) with the arrow 50px down and `max-height` 300, while `left bottom` gives (50,150) and `right bottom` (350,150) with the arrow 150px down, so an `end` align grows the element upward. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.6` Given a target larger than the overlay in both axes (300 by 300 against 200 by 200) and placement `right`, when position is calculated, then the overlay is centered on the target's cross axis at (550,300) with the arrow 100px down and `max-height` 250. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.7` `Divergence:` Given no explicit side offset, when the element is positioned, then it sits 8px from the anchor plus half the arrow height, because the main-axis offset is `gutter + arrowHeight / 2` and `gutter` defaults to 8, falling back to half the arrow height when no gutter is given. (decision needed) [zag]
- [ ] `positioning.positioning.8` `Divergence:` Given no explicit side offset, when the element is positioned, then it sits flush against the anchor edge with no gap, so a 100 tall target at y 250 puts the overlay top at exactly 350. (decision needed) (browser-only) [react-aria]
- [ ] `positioning.positioning.9` Given a side offset of 10, when the element is positioned, then it moves 10px further from the anchor along the main axis and the computed `max-height` shrinks by the same 10px on vertical sides (bottom y 360 with `max-height` 190, top y 40 with `max-height` 190); the offset is applied after any flip, and an explicit `offset.mainAxis` overrides `gutter`. (browser-only) [react-aria, zag]
- [ ] `positioning.positioning.10` Given an align offset of 10 on the cross axis, when the element is positioned, then the element moves 10px one way and the arrow moves 10px the other (bottom x 210 with arrow 90, and -10 gives x 190 with arrow 110); zag reads the cross-axis offset from `offset.crossAxis`, falling back to `shift` only for placements with no align suffix, while the align axis always takes `shift`. (browser-only) [react-aria, zag]
- [ ] `positioning.positioning.11` Given both `offset` and `gutter` explicitly set to null, when the element is positioned, then the offset middleware is skipped entirely and the element touches the anchor. (candidate) [zag]
- [ ] `positioning.positioning.12` Given a target carrying a 20px margin, placement `bottom`, and zero collision padding, offset and arrow size, when position is calculated, then the computed `top` is 0, so the target's own margin does not leak into the offset. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.13` Given the overlay's container has an `offsetParent` that is a `position: relative` element offset 150 from the top, when position is calculated, then coordinates resolve against that positioned ancestor, giving `top: 200px` instead of 350px, and a `top` placement in a 400 tall container anchors at `bottom: 300px`. (candidate) (browser-only) [react-aria]
- [ ] `positioning.positioning.14` Given collision detection against the boundary, when the available space is measured, then it is exposed as a maximum size on the element: `max-height` from the available height for vertical sides and `max-width` from the available width for horizontal sides. (browser-only) [react-aria, zag, corvu]
- [ ] `positioning.positioning.15` Given a same-width option (`sameWidth` or `matchSize`), when the element is positioned, then its `width` is taken from the anchor width for `top` and `bottom` placements and its `height` from the anchor height for `left` and `right`, replacing the default `min-width: max-content`. - [ ] `positioning.positioning.16` Given the positioned element lives in a transformed, overflow-clipping portal host only 120px tall, when available size and shifting are computed, then they are measured against the viewport and not against the host, so `--radix-popper-available-height` grows past 300px; base-ui likewise defaults `shift` to the visual viewport by passing `rootBoundary: undefined`. - [ ] `positioning.positioning.17` Given flipping is on, which is the default, when there is not enough room on the requested side, then the side flips to its opposite and produces the same geometry as that opposite side would have unflipped (a `left` placement with the target flush at (0,0) flips to `right` and lands at (100,50) with the arrow 4px in and `max-height` 500), the collision padding used by flip is the same overflow padding as the rest of the stack, and a side offset of 10 is applied after the flip, giving x 110. - [ ] `positioning.positioning.23` Given `slide` or `overlap` is on, when the shift middleware is assembled, then `slide` maps to the main axis, `overlap` to the cross axis, the overflow padding (default 8) to `padding`, and `limitShift()` is always installed as the limiter. (candidate) [zag]
- [ ] `positioning.positioning.24` Given explicit shift options, when the middleware is assembled, then `rootBoundary: 'layoutViewport'` is passed through as given and cross-axis shifting stays off unless `crossAxis: true` is set. (candidate) [base-ui]
- [ ] `positioning.positioning.25` Given a collision boundary option, when it is resolved, then a function is called to produce the element, the literal string `"clipping-ancestors"` maps to the clipping ancestors boundary, any other value passes straight through, and the resolved boundary is threaded into flip, shift, size and hide alike. - [ ] `positioning.positioning.26` Given a 10 by 20 reference rect at (1,2) and overflow just inside and just past each edge (top 19 then 20, right 9 then 10, bottom 19 then 20, left 9 then 10), when the hide middleware runs, then `referenceHidden` is `false` for the inside case and `true` for each past-the-edge case, and the reference context is the one checked first. - [ ] `positioning.positioning.27` `Divergence:` Given a reference rect that is all zeros with no overflow on any side, when the hide middleware runs, then `referenceHidden` is `true`, because a zero-sized anchor is treated as detached. (decision needed) [base-ui]

- [ ] `positioning.positioning.29` Given a `maxHeight` constraint larger than the space the boundary leaves (450 against 406), when position is calculated, then the computed available height wins at 406px, and given a smaller constraint (150) the constraint wins at 150px. - [ ] `positioning.positioning.30` Given the anchor is flush against the boundary on the requested side, when position is calculated, then the available height collapses to 0 rather than going negative (a `top` placement with the target at (0,0) and a `bottom` placement with the target at (500,500) in a 600 tall viewport both give `max-height` 0). ### Animation and presence

- [ ] `positioning.animation.1` Given a positioned element that has not been measured yet, when it first renders, then it is parked off screen and cannot intercept clicks, so it never flashes at the top left corner: zag uses `pointer-events: none` with `transform: translate3d(0, -100vh, 0)`, and reka uses `position: fixed; left: 0px; top: 0px; transform: translate(0, -200%); min-width: max-content`. [zag, reka]
- [ ] `positioning.animation.2` Given a scale animation on a positioned element, when the transform origin is computed, then it sits on the edge nearest the anchor, at the arrow center where there is an arrow, so the element appears to grow out of the trigger: for a `top` side the origin is `<arrowCenterX>px calc(100% + <offset>px)`, for `bottom` it is `<arrowCenterX>px -<offset>px`, for `left` it is `calc(100% + <offset>px) <arrowCenterY>px`, and for `right` it is `-<offset>px <arrowCenterY>px`. [zag, corvu]
- [ ] `positioning.animation.3` Given a positioned element with an entry animation, when it renders before the first position is computed, then the content carries `animation: none` and the arrow carries `visibility: hidden`, so nothing animates from the pre-measurement position. (candidate) [reka]
- [ ] `positioning.animation.4` Given `overlap` is on and the side axis is vertical, when the absolute shift on y exceeds the side offset so the element now covers the anchor, then the transform origin switches from the arrow to the anchor's vertical center. (candidate) (browser-only) [zag]

### RTL and i18n

- [ ] `positioning.rtl.1` Given an aligned placement on a vertical side, when the direction is RTL, then `start` and `end` swap sides in the transform origin: `bottom-start` and `top-start` give an x origin of `100%` in RTL against `0%` in LTR, and `bottom-end` and `top-end` give `0%` in RTL against `100%` in LTR. (candidate) [reka]
- [ ] `positioning.rtl.2` Given an unaligned vertical placement, or any placement on a horizontal side, when the direction changes, then the origin does not move: plain `bottom` and `top` keep an x origin of `50%` in both directions, and `right-start` and `left-start` keep a y origin of `0%` while `right-end` and `left-end` keep `100%`, because horizontal sides align on the y axis. (candidate) [reka]
- [ ] `positioning.rtl.3` Given no direction is supplied at all, when an aligned placement resolves, then it behaves as LTR, so `bottom-start` and `top-start` give `0%` and `bottom-end` and `top-end` give `100%`. (candidate) [reka]

### Notes and edge cases

- [ ] `positioning.notes.1` Given a test environment with no layout engine, when a position is computed, then every anchor rect is all zeros and the viewport size is fixed, so coordinates resolve to 0, flipping never changes the side, shifting never shifts, available width and height are meaningless, and the arrow offset is 0; every geometry assertion in this file therefore needs a real browser, and the position lands at least one microtask after render because the computation is async. [corvu, reka]
- [ ] `positioning.notes.2` Given `{ x: 0, y: 0, width: 100, height: 100 }`, when a rect is created, then it carries those four values; given five points describing a 10 by 50 box, then the derived rect has width 10, height 50, `minX` and `minY` 0, `maxX` 10, `maxY` 50, `midX` 5, `midY` 25 and a center of (5,25), its corners are top (0,0), right (10,0), bottom (10,50) and left (0,50), and a point on the right edge at (10,25) is reported as contained. (candidate) [zag]
- [ ] `positioning.notes.3` Given an 80 by 100 rect at the origin and a 50 by 45 rect at (60,20), when they are intersected, then the result is the 20 by 45 overlap at (60,20) and the rects are reported as intersecting. (candidate) [zag]
- [ ] `positioning.notes.4` Given a 20 by 20 rect at (20,10) inside a 40 by 30 boundary, when collisions are computed, then the colliding edges are `right` and `bottom`. (candidate) [zag]
- [ ] `positioning.notes.5` Given a 40 by 30 rect, when it is inset by a negative dx, then it grows symmetrically on x to width 60 at x -10, and by a positive dx it shrinks to width 30 at x 5, with y and height untouched; given two rects that touch at y 30, then their union is the 40 by 50 bounding box at the origin. (candidate) [zag]
- [ ] `positioning.notes.6` Given inline styles are turned off, when a position is computed, then no style is written but the computed position is still awaited and reported to the completion callback with device-pixel-rounded coordinates. (candidate) [zag]
- [ ] `positioning.notes.7` Given style restoration is on, when the positioner is torn down, then `transform`, `visibility`, `pointer-events`, the `--x`, `--y`, `--z-index`, reference size, available size and transform origin custom properties, and the arrow's `top`, `right`, `bottom` and `left` are all put back as they were, and the `style` attribute is removed outright when nothing is left in it. (candidate) [zag]
- [ ] `positioning.notes.8` Given a deferred positioner, when it is set up, then the whole setup runs inside a `requestAnimationFrame` and the returned cleanup cancels that frame as well as tearing down the position. (candidate) [zag]
- [ ] `positioning.notes.9` Given a positioned element on a `bottom` or `top` side, when the transform origin custom property is written, then it comes out as `"top center"` and `"bottom center"`, the two halves in the wrong order, so the property is unusable as written. (candidate) [corvu]
- [ ] `positioning.notes.10` Given an aligned placement such as `bottom-start` or `right-end`, when the transform origin custom property is written, then no case matches and it is written as the string `undefined`, leaving the property effectively unset for every aligned placement. (candidate) [corvu]

## Deferred

- Library-internal API shape: prop spreading onto the rendered element, `asChild` and `as` forwarding, composed ref stability and render-loop guards, exported symbol lists, and the `rects` middleware that only republishes Floating UI's rects as middleware data.
- Internal reactivity: the single-signal floating state object, the `floatingStatesMatch` short circuit and its inability to express a reset to `undefined`, the store and root-context plumbing around `useFloating`, and the Solid 2 portability notes about memo and prop-getter placement.
- Test-harness plumbing: the `ResizeObserver` stub reka and corvu need in jsdom, and the microtask flushing needed to observe an async position. Folded the substance into `positioning.notes.1`.
- Sticky positioning when the anchor is partly clipped is untested everywhere we looked, so there is no bullet for the stick-versus-hide choice beyond hide-when-detached. The same goes for `updatePositionStrategy`, `collisionPadding` and `collisionBoundary` as author-facing options. reka's suite explicitly asserts none of them, and only zag's source documents the defaults.
- Unresolved defaults, each written as a `Divergence:` pair: the default side offset (8px plus half the arrow height against flush), the default strategy (`absolute` against `fixed`), and whether an all-zero anchor rect counts as detached.
- The exact default collision padding is only evidenced by zag (8 for overflow padding, 4 for arrow padding). react-aria's 50 is a test fixture value, not a default, so no divergence pair is written for it and zag's numbers stand as the candidate.
- react-aria's per-placement `calculatePosition` table is collapsed to representative cases per topic. The full 13 placement by 7 scenario grid lives in the research file if a number is ever needed.
