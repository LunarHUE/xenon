# Cross-cutting

Behaviors every component shares. Format and tagging follow
`docs/spec/README.md`; ids are prefixed with the section name instead of a
component name, and never change once written.

`[react-only]` marks a bullet that exists because of a React-specific hazard.
It is recorded so the contract survives a React adapter, not because
`@kit/solid` needs it.

## id-generation

- [ ] `id-generation.1` Given a part that needs an id for an `aria-*` reference and no `id` prop, when it renders, then it generates one, and the generated id is stable across re-renders of the same instance. [react-aria, radix, base-ui, zag, reka, headlessui]
- [ ] `id-generation.2` Given two instances of the same component in one document, when both render, then every generated id differs. [react-aria, reka]
- [ ] `id-generation.3` Given a part with an explicit `id` prop, when it renders, then the explicit id wins and every `aria-*` reference pointing at that part uses it. [base-ui, radix, zag, reka]
- [ ] `id-generation.4` Given a popup with a caller-supplied `id`, when the trigger renders, then `trigger[aria-controls]` still equals `popup[id]`. [base-ui]
- [ ] `id-generation.5` Given a provider that injects an id generator, when a part generates an id, then the injected generator is used in preference to the framework's own, and the part's own prefix is still applied: an injected generator returning `provided-id` with prefix `reka-test` yields `reka-test-provided-id`. [reka] (candidate)
- [ ] `id-generation.6` Given a production build with no server render, when ids are generated, then they carry a random prefix so that two independent app instances on one page cannot collide; under `NODE_ENV=test` the random prefix is omitted so snapshots stay stable. [react-aria] (candidate)
- [ ] `id-generation.7` Given a part whose id is later merged with another id, when the merge happens, then both props collapse to one shared id and no infinite merge loop occurs, including when the same id appears twice in the merge input. [react-aria] (candidate)
- [ ] `id-generation.8` Given an id generated for a mounted part, when the part unmounts, then any registry entry keyed on it is released, and when the id changes the previous entry is released before the new one is registered, with the registry key object staying identical. [react-aria] (candidate)
- [ ] `id-generation.9` Given an `aria-labelledby` or `aria-describedby` built from several sources, when it renders, then the value is a whitespace-normalized, deduplicated, space-separated id list. See `prop-merging.7`. [radix, apg]
- [ ] `id-generation.10` Given any id emitted into an `aria-controls`, `aria-labelledby`, `aria-describedby`, `aria-owns` or `aria-activedescendant` reference, when axe runs, then the id resolves to an existing element and is unique in the document, because `aria-valid-attr-value` reports an unresolved reference as incomplete rather than a pass and `duplicate-id-aria` fails at critical impact. [axe]

## ssr

- [ ] `ssr.1` Given any component rendered to a string on the server and then hydrated, when hydration completes, then no hydration mismatch warning is emitted. [react-aria, reka, zag, headlessui, radix]
- [ ] `ssr.2` Given a component whose markup depends on a generated id, when it is server-rendered and hydrated, then the server and client ids match. [react-aria, reka]
- [ ] `ssr.3` Given a closed overlay, when the server HTML is inspected before hydration, then the overlay content is absent from that HTML. [react-aria]
- [ ] `ssr.4` Given a part whose value depends on measurement, when the server HTML is inspected, then the measured value is reported as zero, and after hydration it reports real dimensions. [react-aria] (candidate)
- [ ] `ssr.5` Given a machine or controller rendered on the server, when the render completes, then no teardown or exit action runs, because the server render has no unmount phase. [zag] (candidate)
- [ ] `ssr.6` Given a component that renders differently on the server, when it hydrates, then the environment flag flips from server to client. Headless UI's Vue SSR helper never flips it back, so a Vue component branching on the flag behaves differently in its own tests than in a real app; that asymmetry is a bug to avoid, not a behavior to copy. [headlessui]
- [ ] `ssr.7` Given a void or self-closing tag (`br`, `hr`, `img`, `input`, `area`, `textarea`), when the polymorphic factory renders it, then it renders with no children slot at all, specifically to avoid a hydration mismatch. [ark]
- [ ] `ssr.8` Given a component under `React.StrictMode` with nested SSR providers and `Suspense` boundaries, when server-rendered and hydrated, then ids stay distinct and no hydration error occurs. [react-aria] `[react-only]`
- [ ] `ssr.9` Given a part that emits a server-only marker, when it server-renders, then the marker is present in the server HTML and gone after hydration. Zag emits `data-ssr` on radio-group and tabs roots. [zag] (candidate)
- [ ] `ssr.10` Given the whole package graph imported under a server-components resolution condition, when each entry is imported, then an entry declaring a client boundary is importable from a server component and an entry that does not declare one imports without throwing, so no module-scope code touches a client-only global. [radix] `[react-only]`

## rtl

- [ ] `rtl.1` Given no direction provider, when a component reads the ambient direction, then it is `ltr`. [base-ui, reka, kobalte]
- [ ] `rtl.2` Given a direction provider set to `rtl`, when a descendant reads the direction, then it is `rtl`, and when the provider's value changes the descendant re-reads the new value. [base-ui, reka]
- [ ] `rtl.3` Given a horizontal composite in `ltr`, when the next-item key is resolved, then it is `ArrowRight` and the previous-item key is `ArrowLeft`. [melt, bits, apg]
- [ ] `rtl.4` Given a horizontal composite in `rtl`, when the next-item key is resolved, then it is `ArrowLeft` and the previous-item key is `ArrowRight`. [melt, bits, apg]
- [ ] `rtl.5` Given a vertical composite, when the next-item key is resolved, then it is `ArrowDown` and the previous is `ArrowUp`, **in both directions**: RTL never inverts the vertical axis. [melt, bits]
- [ ] `rtl.6` Given an invalid direction or orientation string, when the directional keys are resolved, then the resolver falls back to the horizontal LTR pair instead of throwing. [bits] (candidate)
- [ ] `rtl.7` Given a positioned part in `rtl`, when it is placed, then `data-side` and `data-align` describe the resolved physical side and alignment, not the logical one. [base-ui, radix, zag]
- [ ] `rtl.8` Given a locale provider with an explicit locale, when the browser locale changes and a `languagechange` event fires, then the explicit locale still wins. [react-aria, kobalte]
- [ ] `rtl.9` Given a locale provider with no explicit locale, when the browser locale changes to an RTL language and `languagechange` fires, then the reported locale and direction both update, and changing back to an LTR language returns the direction to `ltr`. [react-aria, kobalte]
- [ ] `rtl.10` Given a locale, when the direction is derived, then it comes from the locale rather than being passed in separately: `ar-AR` yields `rtl`. The derivation must use the maximized script, not just the language prefix, so a locale whose script rather than language decides direction resolves correctly. Kobalte implements the script path and tests only `ar-AR`, so neither branch is isolated upstream. [kobalte, react-aria]
- [ ] `rtl.11` Given a `languagechange` listener registered by the locale reader, when the owner is disposed, then the listener is removed. Kobalte's test for this is vacuous (its assertions sit inside an `onMount` and an `onCleanup` that never run before `dispose()`), so the behavior is effectively unverified upstream. [kobalte] (candidate)
- [ ] `rtl.12` Given the locale query throws (an unsupported locale tag), when the default locale is resolved, then it falls back to `en-US` rather than propagating. [kobalte] (candidate)
- [ ] `rtl.13` Given a server render, when the locale is resolved, then it is the fixed default and the direction is `ltr`, and it switches to the real locale only after hydration. [kobalte] (candidate)
- [ ] `rtl.14` Given a nested direction or locale provider, when a descendant reads it, then the nearest provider wins. Neither Kobalte nor Reka tests the nested case. [base-ui] (candidate)

## polymorphism

- [ ] `polymorphism.1` Given a part rendered with no override, when it renders, then it emits its default tag. [reka, kobalte, headlessui, base-ui]
- [ ] `polymorphism.2` Given a part with a string tag override, when it renders, then the element is that intrinsic tag and carries every prop the part owns. [reka, kobalte, headlessui, ark]
- [ ] `polymorphism.3` Given a part whose override is a component, when it renders, then the component's own attributes survive alongside the forwarded props, and the rendered element is the component's element. [reka, kobalte, ark]
- [ ] `polymorphism.4` Given the child-delegating form (`asChild`, `as="template"`, `render`, a `child` snippet), when it renders, then the part's own element is absent from the DOM and only the child element is rendered. [radix, base-ui, reka, bits, ark]
- [ ] `polymorphism.5` Given child delegation with a non-element child (plain text, `null`, `undefined`, `false`), when it renders, then nothing is rendered and nothing throws. Ark fails silently with no element and no warning, which is worse than Radix's descriptive error. [radix, ark]
- [ ] `polymorphism.6` Given child delegation with two sibling element children, when it renders, then it throws a descriptive error naming the slot rather than a cryptic framework error. Ark renders nothing at all in this case. [radix]
- [ ] `polymorphism.7` Given child delegation where the child slot starts with a comment node (a conditional-render placeholder), when it renders, then the comment is skipped and the props land on the first element node. [reka, ark]
- [ ] `polymorphism.8` Given child delegation where the slot renders only a comment, when it renders, then the markup is left untouched rather than throwing or injecting a wrapper. [ark] (candidate)
- [ ] `polymorphism.9` Given a slottable marker that lets siblings stay outside the delegated element, when it renders, then the part's props land on the marked element and the sibling nodes end up nested inside it. [radix] (candidate)
- [ ] `polymorphism.10` Given a render-prop form of the slottable marker whose render wraps the child, when it renders, then the part's props land on the resolved child rather than on the wrapper, and the wrapper wraps the child's original children. [radix] (candidate)
- [ ] `polymorphism.11` Given nested parts where both set child delegation, when they render, then the outermost props reach the innermost element; given an intermediate level that opts out, then the chain stops at that level. [ark] (candidate)
- [ ] `polymorphism.12` Given a part whose tag is resolved from a live element reference with a string fallback, when the reference resolves, then the real element's lowercased tag name wins over the fallback; while the reference is unresolved the fallback is used. Nothing upstream asserts it updates reactively once the reference resolves. [kobalte] (candidate)
- [ ] `polymorphism.13` Given a child-delegating part whose child changes tag conditionally, when the condition flips, then the resolved element reference updates. [reka] (candidate)
- [ ] `polymorphism.14` Given a part rendered with a fragment-like pass-through and props that must be forwarded but no element to forward them to, when it renders, then it throws an error naming the component, listing the props it needs to forward, and suggesting either an explicit tag or a single child element. [headlessui] (candidate)
- [ ] `polymorphism.15` Given a part whose ref must be delivered under a different prop name, when it renders with that name configured, then the ref is forwarded as a prop of that name rather than as `ref`. [headlessui] (candidate)
- [ ] `polymorphism.16` Divergence: the Solid and Svelte polymorphic forms take a render function or snippet receiving a props callback, so the delegated child is authored rather than cloned; React and Vue take a boolean and clone the single child. The callback form cannot compose a parent ref the way cloning can. Ark's Solid factory strips `ref` out of the parent props before merging, so a parent ref is simply not forwarded through `asChild`. Decide whether our Solid adapter forwards refs through the delegated child or documents that it does not. [ark] (decision needed)
- [ ] `polymorphism.17` Given a polymorphic part whose element type changes between renders, when it re-renders, then the same DOM element is patched in place rather than replaced. [ark] (candidate)

## prop-merging

- [ ] `prop-merging.1` Given user props and core props for the same part, when they merge, then an ordinary attribute takes the user's value. `docs/architecture.md` fixes this: the user's win. [ark, reka, radix]
- [ ] `prop-merging.2` Given a `class` on both sides, when they merge, then the result is the concatenation of both class lists with no duplicates, and the element carries every class from each side. Order differs upstream: Radix's slot puts the slot's class first (`"slot child"`), Reka's `Primitive` puts the parent's first (`"parent-class child-class more-child-class"`), Ark's factory puts the child's first (`"child parent"`). [radix, base-ui, reka, ark, headlessui]
- [ ] `prop-merging.3` Divergence: class concatenation order. Radix and Reka are parent-first, Ark is child-first. Pick one and pin it, because a consumer relying on later-wins CSS specificity sees different results. [radix, reka, ark] (decision needed)
- [ ] `prop-merging.4` Given a merged class list and a re-render, when the subtree renders again, then the merged value is unchanged and does not accumulate duplicates. [reka, ark]
- [ ] `prop-merging.5` Given an inline `style` on both sides, when they merge, then both declaration sets apply and neither replaces the other. Radix's own test proves this by picking a user property (`outlineColor: rgb(1, 2, 3)`) alongside a library-owned one (`pointer-events: none`, `position: absolute`). Where both sides pass a style string rather than an object, they are concatenated with a `;`; where only one is a string, the other is serialized. [radix, base-ui, ark, zag]
- [ ] `prop-merging.6` Given three style sources (core, user prop, delegated child), when they merge, then all three apply. [base-ui] (candidate)
- [ ] `prop-merging.7` Given `aria-describedby` (or `aria-labelledby`) on both sides, when they merge, then the id lists are concatenated with the child's ids first, whitespace is normalized, and duplicates are removed: `" shared-description  slot-description "` plus `" child-description\tshared-description child-description "` yields exactly `"child-description shared-description slot-description"`. [radix] (candidate)
- [ ] `prop-merging.8` Given an event handler on both sides, when they merge, then both run and neither replaces the other, each exactly once per event. [radix, base-ui, ark, zag, reka]
- [ ] `prop-merging.9` Given an event handler on both sides, when the event fires, then the user's handler runs first and calling `preventDefault()` skips the core handler. This is our contract from `docs/architecture.md`. Upstream ordering disagrees: Radix's slot runs the child's handler first then the slot's; Zag's `mergeProps` composes into a call-all of the later then the earlier handler; Base UI gives the consumer an explicit `event.preventBaseUIHandler()` instead of reusing `preventDefault`. [radix, zag, base-ui] (decision needed)
- [ ] `prop-merging.10` Given a merged handler pair where one side is explicitly `undefined`, when the event fires, then the other side's handler still runs. [radix]
- [ ] `prop-merging.11` Given a merge, when a key is not a handler, not `class` and not `style`, then the later source's value replaces the earlier one; `data-ownedby` is the documented exception and its tokens are concatenated and deduplicated. [zag, ark]
- [ ] `prop-merging.12` Given `undefined` as a prop value, when the props are applied, then the attribute is not set at all; given `null`, then the attribute is removed; given `false`, then it is kept as a meaningful boolean. This is the `PartProps` contract and Zag's vanilla adapter is the reference: `undefined` values are filtered out, `null` and `false` are kept. [zag]
- [ ] `prop-merging.13` Given a ref on both the part and the delegated child, when the element mounts, then both receive the same node. [radix, base-ui, ark]
- [ ] `prop-merging.14` Given a stable callback ref and a re-render of an unrelated parent, when the subtree re-renders, then the ref is not called again: exactly one distinct ref identity is ever handed to the child. [radix, ark] `[react-only]`
- [ ] `prop-merging.15` Given a callback ref that forces a re-render when it receives a node, when the part mounts, then it does not loop: the component renders fewer than 25 times. Radix ships this as `assertStableComposedRef(renderWithRef, { maxRenders = 25 })`. [radix] `[react-only]`
- [ ] `prop-merging.16` Given the set of refs for a part changes between renders (one ref, then two, then a different one), when it re-renders, then every ref in the current set points at the element and a dropped ref is set to null. [base-ui] (candidate)
- [ ] `prop-merging.17` Given a ref on a native text input and typing into it, when the value changes, then the function ref is called only once. Radix skips both of its tests for this pending radix-ui/primitives#3554, so the behavior is unverified upstream. [radix] (candidate) `[react-only]`
- [ ] `prop-merging.18` Given a `class` or `style` passed as a function of the part's state, when it resolves, then the resolved value **merges** with the core value rather than replacing it; when the function returns `undefined`, only the core value applies. [base-ui] (candidate)
- [ ] `prop-merging.19` Given the state-to-attribute mapping, when a state entry is `undefined`, then no attribute is emitted for it; when the state object is empty or absent, then no state attributes are emitted at all and user-supplied attributes are untouched. [base-ui]
- [ ] `prop-merging.20` Given a user-supplied `data-*` attribute whose name collides with one the part would generate, when they merge, then the user's value wins. [headlessui] (candidate)
- [ ] `prop-merging.21` Given a prop key the part does not consume, when it merges, then it lands on the rendered element verbatim. This is Radix's "spreads props it does not consume onto the element it renders" pair, present on every primitive part, and Base UI's `propsSpread` conformance suite. [radix, base-ui]
- [ ] `prop-merging.22` Given symbol-keyed props (a framework's attachment mechanism), when they merge, then symbol keys are copied from the later source with no composition, and a repeated symbol key takes the last value. [zag] (candidate)
- [ ] `prop-merging.23` Given attribute names in the adapter, when they reach the DOM, then they use the HTML spelling (`class`, `for`, `tabindex`), and `value`, `checked` and `selected` are written as DOM properties rather than attributes. [zag]
- [ ] `prop-merging.24` Given a style object containing CSS custom properties, when it is applied, then property names starting with `--` keep their exact case while ordinary camelCase keys are hyphenated. [zag]
- [ ] `prop-merging.25` Given inline styles set on an element from outside the adapter, when the adapter applies its own style object, then the outside styles are not clobbered, and when a property leaves the adapter's style object only that property is removed. [zag] (candidate)
- [ ] `prop-merging.26` Given SVG attributes, when they are applied, then `viewBox` and `preserveAspectRatio` keep their case while other attribute names are lowercased. [zag]

## controlled

- [ ] `controlled.1` Given a controlled value prop, when the component first renders, then the controlled value is shown rather than any default. [radix, base-ui, kobalte, corvu, reka, melt, zag]
- [ ] `controlled.2` Given a controlled value prop, when an interaction would change the value, then `onChange` fires with the new value and the rendered value does **not** move until the prop does. The owner of the prop decides whether the value actually changes. [kobalte, corvu, radix, zag]
- [ ] `controlled.3` Given a controlled value prop, when the prop changes externally, then the rendered value follows and `onChange` does **not** fire. An external change never echoes back. [kobalte, radix]
- [ ] `controlled.4` Given an uncontrolled component with a default value, when it first renders, then the default is shown and `onChange` has not fired. Mounting never fires `onChange`. [kobalte, radix, zag]
- [ ] `controlled.5` Given an uncontrolled component, when an interaction changes the value, then internal state moves **and** `onChange` fires with the new value. [kobalte, corvu, radix, zag]
- [ ] `controlled.6` Given a set to a value that is `Object.is`-equal to the current one, when it runs, then neither internal state is written nor does `onChange` fire. A no-op set is completely silent. This is the single rule most likely to be got wrong and it is the difference between one and two change events per interaction. [kobalte, corvu, zag, ariakit]
- [ ] `controlled.7` Given the current value is `NaN`, when it is set to `NaN` again, then `onChange` does not fire a second time, because the equality gate is `Object.is` and not `===`. [kobalte, base-ui, ariakit]
- [ ] `controlled.8` Given the current value is `0`, when it is set to `-0`, then that counts as a change, because the gate is `Object.is`. [base-ui] (candidate)
- [ ] `controlled.9` Given a setter called with an updater function, when it runs, then the updater receives the **currently resolved** value (the controlled one while controlled, the internal one otherwise) and its return value is committed through the same equality gate. [kobalte, corvu, radix, zag, ariakit]
- [ ] `controlled.10` Given an updater that returns the current value, when it runs, then `onChange` does not fire. [kobalte]
- [ ] `controlled.11` Given a custom equality function, when a set runs, then it is used instead of `Object.is`. [zag] (candidate)
- [ ] `controlled.12` Given a setter call, when it runs, then the read of the current value does not create a reactive dependency on the calling scope: the body runs untracked. [corvu] (candidate)
- [ ] `controlled.13` Given the value prop is `undefined`, when the component reads it, then the component is **uncontrolled** and falls back to its internal state. `undefined` is the sentinel, not `null` and not absence of the prop, so a controlled value can legitimately hold `null` but never `undefined`. [corvu, base-ui, radix]
- [ ] `controlled.14` Given a component that starts uncontrolled and is later handed a defined value prop, when that happens, then a development warning is logged naming the component, and the value follows the prop from then on. Radix's exact text: "<Name> is changing from uncontrolled to controlled. Components should not switch from controlled to uncontrolled (or vice versa). Decide between using a controlled or uncontrolled value for the lifetime of the component." Base UI's: "Base UI: A component is changing the uncontrolled value state of <Name> to be controlled." [radix, base-ui]
- [ ] `controlled.15` Given a component that starts controlled and whose value prop later becomes `undefined`, when that happens, then a development warning is logged, the value falls back to the default, and further sets do **not** move it: the component does not adopt internal state after the switch. [radix, base-ui]
- [ ] `controlled.16` Given a default-value prop that changes after the first render while uncontrolled, when it changes, then a development warning is logged exactly once no matter how many times it changes afterwards. [base-ui] (candidate)
- [ ] `controlled.17` Given a component that is controlled, when its default-value prop changes, then no warning is logged, because the default is irrelevant while controlled. [base-ui] (candidate)
- [ ] `controlled.18` Given a default value that is a fresh array or object each render, contains functions or framework elements, is `NaN`, is a bigint, or is `null`/`undefined`, when the change detection runs, then it neither warns nor throws. A JSON-based comparison throws on a bigint, so the comparison must not be JSON-based. [base-ui] (candidate)
- [ ] `controlled.19` Given a single-selection component whose current value is reselected, when the selection runs, then the value clears to `undefined`. Given a multiple-selection component, then selection toggles per item. [reka] (candidate)
- [ ] `controlled.20` Given a component with no explicit selection-mode prop, when the value is a string, then it behaves as single; when it is an array, then multiple. An explicit mode prop wins over the inferred one and coerces the value's shape. [reka] (candidate)
- [ ] `controlled.21` Given a change callback that returns a value, when a set runs, then the callback's return value decides the committed state and the callback receives both the current and the next value. [melt] (candidate)
- [ ] `controlled.22` Given a component under `React.StrictMode`, which double-invokes renders and effects, when it mounts, then generated ids are not doubled up, entry-effect cleanups are composed rather than overwritten across the double mount, mutations made by entry effects are fully reverted on close, and unmounting fires every entry-effect cleanup. [zag, react-aria] `[react-only]`
- [ ] `controlled.23` Given a component under `React.StrictMode`, when a mocked getter is read, then it is read twice per logical read. React Aria's `mockImplementation()` registers each `mockImplementationOnce` twice for exactly this reason. [react-aria] `[react-only]`
- [ ] `controlled.24` Given a captured setter or command API, when the component re-renders, then it keeps referential identity and keeps working after prop-driven changes, so an effect depending on it runs once. [zag] `[react-only]`
- [ ] `controlled.25` Given several sets in one tick, when they are processed, then the result is deterministic; and given two tagged sets of the same kind in one tick, then the later replaces the earlier and untagged sets are never replaced. [zag] (candidate)
- [ ] `controlled.26` Given a set after teardown or unmount, when it runs, then it is ignored. [zag] (candidate)
- [ ] `controlled.27` Given an explicitly empty value (an empty string, an empty array), when it is set before render, before items load, or through the state setter, then it is preserved rather than replaced by the first available item. [ariakit] (candidate)

## disabled

- [ ] `disabled.1` Given a part rendered as a native control and marked disabled, when it renders, then it carries the native `disabled` attribute plus `data-disabled` and **not** `aria-disabled`; Tab does not focus it; and clicking, Space and Enter fire none of its handlers. [base-ui, html, react-aria]
- [ ] `disabled.2` Given a part rendered as a non-native element and marked disabled, when it renders, then it carries `data-disabled`, `aria-disabled="true"` and `tabindex="-1"` and **no** native `disabled` attribute; Tab does not focus it; and clicking, Space and Enter fire none of its handlers. [base-ui, zag, kobalte]
- [ ] `disabled.3` Given a part marked disabled but required to stay discoverable, when it renders, then it uses `aria-disabled="true"` and drops the native `disabled` attribute, keeping `tabindex="0"`; Tab **does** focus it, yet clicking, Space and Enter still fire none of its handlers. The APG requires this for a trigger whose action is temporarily unavailable, for alert dialog confirm and cancel buttons, and for toolbar controls. [apg, base-ui, ariakit, zag]
- [ ] `disabled.4` Given `aria-disabled="true"` alone, then the browser supplies **no** click suppression, **no** focus exclusion and **no** constraint-validation exemption, so every one of those behaviors has to be implemented in script. [apg, html]
- [ ] `disabled.5` Given a focusable-when-disabled part, when it is hovered, then hover handlers still fire while activation stays blocked. [base-ui] (candidate)
- [ ] `disabled.6` Given a focusable-when-disabled part that disables itself inside its own activation handler, when it is activated once, then the handler fires once, the part keeps focus, it gains `aria-disabled="true"`, and further activations do nothing. [base-ui] (candidate)
- [ ] `disabled.7` Given a disabled trigger for an overlay, when it is clicked, then the overlay does not open, and when the open handler is reached with `aria-disabled="true"` it refuses to open. [apg, base-ui]
- [ ] `disabled.8` Given a disabled item inside a collection, when the roving tabindex is computed, then the item is allowed to drop its `tabindex`: the `tabindex="-1"` requirement applies only to items whose `aria-disabled` is not truthy. [headlessui]
- [ ] `disabled.9` Given a disabled item in a single-select collection, when it renders, then `aria-selected` is omitted entirely rather than set to `"false"`, and the item carries `aria-disabled` and `data-disabled`. [zag] (candidate)
- [ ] `disabled.10` Divergence: whether an enabled item renders `aria-disabled="false"` explicitly or omits the attribute. The APG menubar editor example requires the explicit `"false"`; Headless UI's radio group omits it entirely on enabled options; Kobalte's listbox renders every option with an explicit `aria-selected="false"` and `aria-disabled="false"` while its own radio group omits `aria-disabled`. Pick one and apply it everywhere, because a test that asserts absence fails against a library that asserts presence. [apg, headlessui, kobalte] (decision needed)
- [ ] `disabled.11` Given a disabled control inside a form, when the form is submitted, then the control contributes nothing to the submitted data. [headlessui, html]
- [ ] `disabled.12` Given a disabled fieldset or a disabled field wrapper, when a descendant control renders, then the descendant is disabled too, either through the native `disabled` attribute or through `aria-disabled="true"` inherited from context. [headlessui, base-ui]
- [ ] `disabled.13` Given a disabled control and a label associated with it, when the label is clicked, then focus does not move to the control and stays where it was. This holds whether the control itself, its field wrapper or its fieldset is disabled. [headlessui]
- [ ] `disabled.14` Given a disabled control with a required attribute, when validity is read, then the validation message is empty; when the control is re-enabled it is non-empty. [ariakit, html] (candidate)
- [ ] `disabled.15` Given a native disabled element, when a click gesture is simulated on it, then it receives the pointer-family events (`pointerdown`, `pointerup`) but not the mouse-family ones (`mousedown`, `mouseup`) and not the terminal `click`. Headless UI's test helper fires nothing at all on a disabled button, which is not what a browser does. [ariakit, html]
- [ ] `disabled.16` Given a non-primary-button gesture on a native disabled element, when it completes, then `auxclick` still fires in Chromium and WebKit and does not in Firefox. [ariakit] (browser-only)
- [ ] `disabled.17` Given a disabled element, when a script dispatches a click on it, then the listener still runs, per spec and per every real engine. happy-dom drops scripted clicks on disabled controls, contrary to spec, jsdom and browsers. [ariakit, html]
- [ ] `disabled.18` Given a disabled checkbox or radio, when a script dispatches a click on it, then activation behavior runs (the checkbox toggles in either direction and clears `indeterminate`; the radio becomes selected) and `input` then `change` fire only when the value actually committed; if a listener prevents the click, only the activation's own changes are reverted and a listener's changes to other controls are preserved. [ariakit, html] (candidate)
- [ ] `disabled.19` Given a disabled submit or reset control, when a click is dispatched on it, then the form is neither submitted nor reset. [ariakit, html]
- [ ] `disabled.20` Given a form whose default submit button is disabled, disabled by an ancestor fieldset, or is a disabled image submitter, when Enter is pressed in a text input, then the form is not submitted. [ariakit, html]
- [ ] `disabled.21` Given a part disabled with `aria-disabled="true"` rather than the native attribute, when axe runs, then no rule objects: axe's focusability model reacts only to the native `disabled` attribute, to `inert`, and to hiding. So `aria-hidden-focus` is not triggered by an accessibly-disabled but focusable control. [axe]
- [ ] `disabled.22` Given a part that is both disabled and focusable, when it renders, then `tabindex` is `0`; given it is disabled and not focusable, then `tabindex` is `-1` or absent. Never a positive `tabindex`: axe's `tabindex` rule fails any value greater than 0 at serious impact, so a roving tabindex must only ever use `0` and `-1`. [axe, apg]
- [ ] `disabled.23` Given a disabled item and keyboard-driven selection, when a test driver tries to toggle it, then the attempt throws rather than silently doing nothing. React Aria's testers make this explicit. [react-aria] (candidate)
- [ ] `disabled.24` Given a collection with a disabled-behavior setting of "selection only", when an item is disabled, then it carries no `aria-disabled` and no `aria-selected`, its selection checkbox is disabled, but interactive controls inside it stay enabled. [react-aria] (candidate)
- [ ] `disabled.25` Given a disabled item and focus moving through the collection, when the next candidate is disabled, then focus skips past it. [react-aria, apg]
- [ ] `disabled.26` Given a disabled or read-only control, when text is typed into it, then the value does not change and no `input` event fires. Kobalte's text field has no test for this; it only asserts the attributes are set. [ariakit, html]
- [ ] `disabled.27` Given a real browser, when an element disables itself while focused, then the browser blurs it; happy-dom does not. [ariakit] (browser-only)

## data-attributes

The full per-component inventory and the proposed canonical set live in
`docs/spec/styling-contract.md`. These bullets are the rules the suite checks on
every component.

- [ ] `data-attributes.1` Given a boolean state that is true, when the part renders, then the attribute is present with an **empty** value; given it is false, then the attribute is absent entirely. Never `="false"`, never `="true"`. [radix, base-ui, zag, kobalte, reka, melt, bits]
- [ ] `data-attributes.2` Given an enumerated state, when the part renders, then it is one `data-state` attribute whose value comes from a fixed set (`open`/`closed`, `checked`/`unchecked`/`indeterminate`, `on`/`off`), not a pair of presence attributes. [radix, zag, kobalte, reka, melt, bits]
- [ ] `data-attributes.3` Given any rendered part, when it renders, then it carries `data-scope="<component>"` and `data-part="<part>"`, both kebab-cased, and every piece of state is an additional `data-*` attribute on those same elements so that styling never depends on class names. [zag, ark]
- [ ] `data-attributes.4` Given a camelCase component or part name, when the attributes are emitted, then both are kebab-cased: a component named `hoverCard` with a part named `toggleButton` yields `data-scope="hover-card"` and `data-part="toggle-button"`. [zag]
- [ ] `data-attributes.5` Given a part with a duplicated name in its anatomy declaration, when the anatomy is built, then the part appears once; and given an anatomy extended with extra parts, then duplicates between base and extension are collapsed. [zag] (candidate)
- [ ] `data-attributes.6` Given a component built by renaming another's anatomy, when it renders, then every part's `data-scope` switches to the new name while the part names stay. [zag] (candidate)
- [ ] `data-attributes.7` Given an input-backed control (checkbox, switch, radio, slider thumb), when its state changes, then the state attributes go on the **visible** part rather than on the hidden input, because that is what CSS can reach. [zag, kobalte]
- [ ] `data-attributes.8` Given a part with focus, when the focus came from a pointer, then it carries `data-focus` and **not** `data-focus-visible`; when it came from the keyboard, then it carries both. [zag, kobalte, react-aria]
- [ ] `data-attributes.9` Given a part with validation state, when validation has not yet run, then neither `data-valid` nor `data-invalid` is present; afterwards exactly one of them is. [base-ui, kobalte]
- [ ] `data-attributes.10` Given the enter phase of a transition, when the part renders, then it carries `data-starting-style` for exactly one commit, and the part's own state attribute (`data-open`, `data-state="open"`) is present in the **same** commit. [base-ui] (browser-only)
- [ ] `data-attributes.11` Given the exit phase of a transition, when it begins, then the part synchronously gains `data-ending-style` and is removed from the DOM only after the animation finishes. [base-ui, bits] (browser-only)
- [ ] `data-attributes.12` Given a transition-status mapping, when the status is neither starting nor ending, then no transition attribute is emitted at all. [base-ui]
- [ ] `data-attributes.13` Given a state value of `undefined`, when the state-to-attribute mapping runs, then no attribute is emitted for that key. [base-ui]
- [ ] `data-attributes.14` Given a part in a collection, when it renders, then `data-value` carries the stringified item value and `data-index` the zero-based position, so a page-object suite can locate an item without a test id. [zag]
- [ ] `data-attributes.15` Given a namespaced plumbing attribute (a portal marker, a focus guard, a scroll-lock marker, an inert marker), when it renders, then it is not treated as a styling hook and no component's public contract depends on it. [base-ui, radix, reka, zag]
- [ ] `data-attributes.16` Given a part that sets a CSS custom property, when the property is measured in a simulated DOM, then it reads zero or empty, so every bullet about a custom property is `(browser-only)`. Reka sets all five of its popper properties and asserts none of them; the collapsible and accordion content-height properties are likewise untested everywhere. [reka, base-ui, zag] (browser-only)

## a11y-tooling

- [ ] `a11y-tooling.1` Given any component in any of its meaningful states, when axe runs over its rendered subtree, then there are no violations. One assertion per meaningful state (closed and open, single and multiple, enabled and disabled), not one per component. Reka's convention is a test named "should pass axe accessibility tests" per `describe` block, repeated per state, which gives a five-state component five audits. [radix, reka, melt, zag, ark]
- [ ] `a11y-tooling.2` Given a component fragment mounted without a landmark wrapper, when axe runs, then the `region` rule is disabled, because the fragment legitimately has no landmark. Reka configures this globally; Melt does not, so the rule is active there and its audits are correspondingly noisier. [reka]
- [ ] `a11y-tooling.3` Given a component rendered without real styles, when axe runs, then `color-contrast` is disabled, because there is nothing to measure. Zag's `checkAccessibility` disables it on every call even in a real browser. [zag]
- [ ] `a11y-tooling.4` Given axe's own defaults, when the suite is configured, then `target-size`, `aria-roledescription` and the deprecated `duplicate-id-active` are enabled explicitly, because they ship disabled and would otherwise never run. `target-size` is the WCAG 2.2 AA 24-by-24-pixel check and is `(browser-only)`. [axe]
- [ ] `a11y-tooling.5` Given axe asks for pseudo-element styles, when it runs in jsdom, then `getComputedStyle` must tolerate the pseudo-element argument. jsdom throws "Not implemented" and axe asks on every audit, so Reka monkey-patches `getComputedStyle` to drop the argument. Without that patch every audit fails for the wrong reason. [reka]
- [ ] `a11y-tooling.6` Given a scoped audit, when the scope is chosen, then it is the component's root part; for a portalled part the scope has to widen to the whole page, because the content is not inside the root. Zag's menu model overrides `checkAccessibility` to scan `main` for exactly this reason. [zag]
- [ ] `a11y-tooling.7` Given any `role` attribute the library emits, when axe runs, then the role is valid, non-abstract, non-deprecated and widely supported; `invalidrole` and `unsupportedrole` are critical, `abstractrole` is serious, and a deprecated role is minor. [axe]
- [ ] `a11y-tooling.8` Given any `aria-*` attribute the library emits, when axe runs, then the name is valid, the value is valid for that attribute, the attribute is allowed for the element's role and host element, and it is not deprecated or poorly supported. All critical impact. [axe]
- [ ] `a11y-tooling.9` Given any role the library emits, when axe runs, then every ARIA attribute that role requires is present. Critical impact, message "Required ARIA attribute not present". [axe]
- [ ] `a11y-tooling.10` Given a part with `role="none"` or `role="presentation"`, when it renders, then it carries neither `aria-label` nor `aria-labelledby` and is neither focusable nor carrying a global ARIA attribute. [axe]
- [ ] `a11y-tooling.11` Given a part with `aria-hidden="true"`, when it renders, then neither it nor any descendant is focusable. The `inert` attribute is the cleaner fix than `tabindex="-1"` on descendants, because axe's focusability model treats inert content as not focusable. Only the outermost `aria-hidden="true"` element is tested. [axe, apg]
- [ ] `a11y-tooling.12` Given a trigger with a widget role, when it renders, then it contains no focusable widget-role descendant, and a negative `tabindex` on the nested control is explicitly not an acceptable fix. [axe]
- [ ] `a11y-tooling.13` Given a scrollable region the library creates, when it renders, then it contains a focusable element or is itself focusable. [axe]
- [ ] `a11y-tooling.14` Given a part whose visible text differs from an `aria-label` we add, when axe runs, then the visible text is part of the computed accessible name. [axe]
- [ ] `a11y-tooling.15` Given a non-interactive element the library gives `tabindex="0"`, when it renders, then it carries a widget or composite role. `button` satisfies this; `tooltip`, `dialog`, `alertdialog` and `tabpanel` satisfy only the scrollable-region branch. [axe]
- [ ] `a11y-tooling.16` Given the accessible name of a part, when it is asserted, then the resolution order is `aria-labelledby` (join every referenced element's text with a single space, compare for equality), then `aria-label` (exact), then an associated `label` element (containment), then the part's own text content (containment), stopping at the first source found. [headlessui]
- [ ] `a11y-tooling.17` Given a multi-id `aria-describedby`, when it is asserted, then every id resolves and every referenced element has non-empty text. Headless UI's `assertDescriptionValue` reads the whole attribute as a single id and so cannot verify a multi-id value; the APG's `assertAriaControls` has the same single-id limitation and its mixed-checkbox test hand-rolls the multi-id version. Write the multi-id version once. [apg, headlessui]
- [ ] `a11y-tooling.18` Given a part that advertises virtual focus, when focus is asserted, then an element counts as focused if the document's active element points at it through `aria-activedescendant`, and the assertion additionally requires that real DOM focus is on the container. Ariakit overrides `toHaveFocus` globally to do the first; the APG's `assertAriaActivedescendant` does both. [ariakit, apg]
- [ ] `a11y-tooling.19` Given a real browser, when a name or role needs verifying, then it is read from the engine's computed accessibility tree rather than from DOM attributes. No simulated DOM computes that tree. [ariakit] (browser-only)
- [ ] `a11y-tooling.20` Given an unexpected `console.error` or `console.warn` during any test, when the test ends, then the test fails. Two suites enforce this and it is the cheapest way to catch a whole class of adapter bug; the cost is that a test legitimately expecting a warning has to spy first. [react-aria, ariakit]
- [ ] `a11y-tooling.21` Given a real browser run, when the whole suite is audited, then the browser tier is the one that can prove the `(browser-only)` accessibility bullets. Bits runs every component test in chromium and webkit and has **no** axe anywhere, which is a real gap given that axe works better in a real engine than in jsdom. [bits]

## reduced-motion

- [ ] `reduced-motion.1` Given `prefers-reduced-motion: reduce`, when an overlay opens, then no enter animation runs, and the same holds for its backdrop. [ariakit] (browser-only, chromium-only upstream)
- [ ] `reduced-motion.2` Given `prefers-reduced-motion: reduce`, when an overlay closes, then no exit animation runs and the part is removed on the next commit rather than waiting for an animation that will never fire. [ariakit] (browser-only)
- [ ] `reduced-motion.3` Given `prefers-reduced-motion: reduce`, when an indeterminate progress indicator renders, then it shows a fixed segment or arc instead of animating. [ariakit] (candidate) (browser-only)
- [ ] `reduced-motion.4` Given `prefers-reduced-motion: reduce` and a scroll-into-view that would otherwise be smooth, when it runs, then it scrolls with `behavior: 'auto'`, and a scroll already in progress or already settled is not restarted. [base-ui] (candidate) (browser-only)
- [ ] `reduced-motion.5` Given a part whose exit is instant (no animation and no transition configured), when it closes, then it is removed immediately and never receives `data-ending-style`, because there is nothing to animate. [base-ui]
- [ ] `reduced-motion.6` Given a part with a zero measured size, when it closes, then it unmounts without waiting for an unrelated transition on another property. [base-ui] (candidate) (browser-only)
- [ ] `reduced-motion.7` Given a simulated DOM, when the presence logic reads `getComputedStyle(el).animationName` to decide whether an exit is instant, then the empty string must be treated as `none`. jsdom returns `""`, the comparison against the literal `"none"` fails, the primitive concludes an animation is running, and it waits forever for an `animationend` jsdom will never dispatch. This is the cause of thirteen commented-out assertions in Kobalte, every one of them the negative assertion after a close. [kobalte, corvu]
- [ ] `reduced-motion.8` Given a simulated DOM, when the presence logic reads `getComputedStyle(el).transitionDuration`, then the check must be `NaN`-safe. jsdom returns `""`, `parseFloat("")` is `NaN`, and `NaN === 0` is false, so a drawer never finishes opening or closing under test. [corvu]
- [ ] `reduced-motion.9` Given a part that is initially open, when it first mounts, then its mount animation is suppressed: the part has its open-state attribute but no running animation and a computed `animation-name` of `none`. Suppression applies only to the initial mount, so a later close and reopen each run exactly one animation. [base-ui] (browser-only)
- [ ] `reduced-motion.10` Given a close animation interrupted by a reopen, when the stale close animation later finishes, then the part stays open, never regains `data-starting-style`, and is still the same DOM element. [base-ui] (browser-only)
- [ ] `reduced-motion.11` Given both a CSS transition and a CSS keyframe animation on the same part, when it opens, then a development warning is logged saying only one of the two should be used. [base-ui] (candidate)
- [ ] `reduced-motion.12` Given the suite's default configuration, when a component with animations renders, then animations are disabled, and a test that needs real animation opts in explicitly and restores the flag afterwards. Base UI sets `BASE_UI_ANIMATIONS_DISABLED = true` globally and re-sets it in `afterEach`; that default is worth copying, because it keeps every non-animation test off the clock. [base-ui]
- [ ] `reduced-motion.13` Given an animation-sequence assertion, when it is written, then it observes the **sequence** of `data-starting-style` and `data-ending-style` over time through a `MutationObserver` rather than sampling one state. Bits' `observeTransitionAttrs(node)` is the only honest way to test enter and exit styling. [bits] (browser-only)

## Notes and edge cases

- Two upstream tests for the animation-completion contract are disabled and are gaps worth closing in our suite rather than inheriting. Base UI's `popupConformanceTests` calls `skip()` unconditionally on "removes the popup when the animation finishes" with the comment "XXX: revisit after feedback from the team"; had it run it would inject a `@keyframes` bound to `[data-ending-style]`, keep the portal mounted, close the popup, and assert the popup becomes inaccessible while still mounted and that the animation-end callback fires exactly once. [base-ui]
- Kobalte's thirteen `skipIf(GITHUB_ACTIONS)` cases are each either a real Tab-driven focus move or an interleaving of fake timers with microtask flushes, so its Tab-order behavior and its timer-driven behavior are both unverified in CI. The technique that does work in jsdom is dispatching focus events directly (`focusIn`) rather than driving Tab. See `docs/spec/test-infrastructure.md`. [kobalte]
- Neither Kobalte's nor Corvu's controlled-signal tests switch between controlled and uncontrolled at runtime, start controlled with an `undefined` value, pass both a value and a default, or feed `onChange` back into the controlling signal so the value really moves. All four combinations are in the bullets above and none has upstream evidence. [kobalte, corvu]
- Kobalte's `Polymorphic` throws with "[kobalte]: Polymorphic is missing the required `as` prop." and that error is untested; its two tests check only the rendered element's constructor and one id, so ref forwarding, class and style merging, handler composition between the wrapper and the target component, and children preservation are all uncovered there. Radix's slot test file, from which it was ported, covers all of them. [kobalte, radix]
- Ark's Solid and Svelte factory suites are visibly thinner than its React one: Solid has no prop-override test, no `asChild` propagation test, no ref test and no lazy-boundary tests; Svelte covers only render-only-child, prop override, style and class merge, and event merge. Every `asChild` ref and server-boundary behavior in the research is pinned in React alone. [ark]
- Melt's builder model makes `polymorphism.*` unanswerable: the builder returns a prop bag the consumer spreads onto whatever element it likes, so there is no delegation question. Reka tests `asChild`/`as` through `Primitive`, Bits tests the Svelte `child` snippet, Melt has no equivalent. That asymmetry is the single biggest difference in what the three suites can even express. [reka, bits, melt]
- Headless UI aggregates state into one space-separated `data-headlessui-state` token list alongside the individual attributes, and its Tailwind plugin compiles `ui-open:` variants into `[data-headlessui-state~="open"]` selectors plus an ancestor form. The aggregate is redundant with the individual attributes and we should not emit one. [headlessui]
