# Number field

One `##` section. The component ships as NumberField (kobalte, reka, react-aria,
base-ui), NumberInput (zag, ark) and the APG spinbutton pattern. Standalone
spinbutton primitives (`useSpinButton`, kobalte's `SpinButton`) and the number
parsing and stepping utilities are folded in here, because they only exist to
serve this component.

Bullets tagged `[apg]`, `[html]` or `[axe]` come from a standard or a linter
rather than a library, so they are normative and never carry `(candidate)`.

## number-field

### Roles and attributes

- [ ] `number-field.roles-and-attributes.1` Given the focusable element serving as a number field, then it MUST have `role="spinbutton"`, and it is typically an element that supports text input. [apg]
- [ ] `number-field.roles-and-attributes.2` Given a spinbutton, then `aria-valuenow` MUST be a decimal representing the current value, and `aria-valuetext` MUST be set when the bare number is not user-friendly. [apg]
- [ ] `number-field.roles-and-attributes.3` Given a spinbutton with a known minimum or maximum, then `aria-valuemin` and `aria-valuemax` MUST be set; where there is no known bound the attribute MUST be omitted. Unlike every other range role, `spinbutton` has NO default limits, so an unset bound exposes no limit rather than 0 or 100, and an unset `aria-valuenow` exposes no value. [apg]
- [ ] `number-field.roles-and-attributes.4` Given a spinbutton with a visible label, then that label MUST be referenced by `aria-labelledby`, otherwise `aria-label` MUST supply the name; axe requires a name from `aria-label`, `aria-labelledby` or `title` at serious impact and does NOT accept visible text content as a name source. [apg, axe]
- [ ] `number-field.roles-and-attributes.5` Given a spinbutton whose current value is outside the allowed range, then `aria-invalid` MUST be `"true"`, and a validation message MUST be referenced by `aria-errormessage`; `aria-invalid` MUST be absent rather than `"false"` when the value is valid. [apg]
- [ ] `number-field.roles-and-attributes.6` Given `role="spinbutton"` in the axe role table, then it has NO required attributes (`aria-valuenow`, `aria-valuemin` and `aria-valuemax` are allowed but implicit), its superclasses are `composite`, `input` and `range`, a name is required, and children are NOT presentational, which is why nested increment and decrement buttons are legal and `nested-interactive` does not apply. [axe]
- [ ] `number-field.roles-and-attributes.7` Given a number field, then the visible input is `type="text"`, never `type="number"`, so the component owns parsing and formatting. [react-aria, base-ui, zag, reka]
- [ ] `number-field.roles-and-attributes.8` Given the wrapper around the input and the steppers, then it is `role="group"` carrying `aria-disabled` and `aria-invalid`. [apg, react-aria, base-ui, zag]
- [ ] `number-field.roles-and-attributes.9` Given increment and decrement buttons, then each MUST reference the spinbutton with `aria-controls` pointing at the input id and MUST have its own accessible name, defaulting to "Increase" and "Decrease"; a symbolic glyph inside a stepper MUST carry `aria-hidden="true"`. [apg, react-aria, base-ui, zag]
- [ ] `number-field.roles-and-attributes.10` Given a label string, then composed stepper names are derived from it ("Increase Width", "Decrease Width"); given a JSX label or an `aria-labelledby`, the steppers fall back to plain "Increase" and "Decrease" plus an `aria-labelledby` of "<ownId> <labelId>" because the text cannot be interpolated. Explicit increment and decrement label props override only their own button. [react-aria] (candidate)
- [ ] `number-field.roles-and-attributes.11` Given the value at the minimum, then the decrement button MUST expose `aria-disabled="true"`, and at the maximum the increment button MUST; otherwise the attribute MUST be absent rather than `"false"`. [apg, react-aria]
- [ ] `number-field.roles-and-attributes.12` Given a typed but uncommitted value beyond a bound, then the stepper for that direction is already disabled before any commit, and clearing the field re-enables it. [react-aria, base-ui]
- [ ] `number-field.roles-and-attributes.13` Given step snapping with bounds, then a stepper is disabled only when no aligned value remains in that direction: with `max: 10`, `step: 3` and value 8 increment stays enabled (9 is reachable) and is disabled at 9; with `min: 2`, `step: 3` and value 4 decrement stays enabled (2 is reachable) and is disabled at 2. [reka, react-aria]
- [ ] `number-field.roles-and-attributes.14` Given a read-only number field, then the input carries `readonly` and the steppers expose `aria-disabled="true"` rather than `aria-readonly` (invalid on the button role) and rather than the native `disabled` attribute, so they stay discoverable. [react-aria, base-ui]
- [ ] `number-field.roles-and-attributes.15` Given `disabled`, `readOnly` or `required`, then the input carries both the native attribute and its ARIA counterpart (`aria-disabled`, `aria-readonly`, `aria-required`), and the root and input both carry the matching `data-*` attribute. [kobalte, zag, reka]
- [ ] `number-field.roles-and-attributes.16` Given a plain number field, then neither the root nor the input carries any of `data-valid`, `data-invalid`, `data-required`, `data-disabled` or `data-readonly`; each appears only in its own state. [kobalte] (candidate)
- [ ] `number-field.roles-and-attributes.17` Given a field wrapper, then the input picks up `data-touched` after a focus and blur, `data-dirty` after the first change, `data-filled` while it holds a value, and `data-focused` on every focus (not only the first), even when the field is read-only. [base-ui] (candidate)
- [ ] `number-field.roles-and-attributes.18` Given the anatomy, then the parts are root, label, control (group), input, valueText, increment trigger, decrement trigger and scrubber; the scrubber is `role="presentation"` with `data-disabled` and `data-scrubbing`. [zag, base-ui]
- [ ] `number-field.roles-and-attributes.19` Given the input, then it carries `aria-roledescription` naming the widget ("numberfield" or "Number field") so screen readers announce it as more than a text box. [react-aria, zag]
- [ ] `number-field.roles-and-attributes.20` Given the input, then `autocomplete="off"` is set, and a `pattern` attribute is dropped whenever format options are in play because the formatted text will not match it. [zag] (candidate)
- [ ] `number-field.roles-and-attributes.21` Given a set of related spinbuttons such as day, month and year, then they SHOULD be wrapped in `role="group"` with `aria-labelledby`, and adjacent "previous value" and "next value" peek displays MUST carry `aria-hidden="true"` because they duplicate exposed information. [apg]
- [ ] `number-field.roles-and-attributes.22` Given a spinbutton whose values map onto names, as a month does, then `aria-valuenow` carries the index and `aria-valuetext` carries the name, for example `aria-valuemin="0"` and `aria-valuemax="11"` with month names in `aria-valuetext`. [apg]
- [ ] `number-field.roles-and-attributes.23` Given a negative value with a text value, then `aria-valuenow` keeps the ASCII hyphen while `aria-valuetext` substitutes U+2212 MINUS SIGN, because screen readers read a hyphen as a dash; announcements use the minus sign too. [react-aria, kobalte]
- [ ] `number-field.roles-and-attributes.24` Given a string value such as `"1,402"` on a spinbutton primitive, then `aria-valuenow` is that string verbatim; the primitive does not coerce or reformat it. [kobalte, react-aria]
- [ ] `number-field.roles-and-attributes.25` Given the steppers hidden by a prop, then neither renders; at large or quiet visual scales both still render. [react-aria] (candidate)
- [ ] `number-field.roles-and-attributes.26` Divergence: the input is `role="spinbutton"` with `aria-valuenow`, `aria-valuemin`, `aria-valuemax` and `aria-valuetext` kept in sync (`aria-valuenow` omitted when the parsed value is NaN). [apg, axe, kobalte, zag] (decision needed)
- [ ] `number-field.roles-and-attributes.27` Divergence: the input has NO `role` and exposes none of `aria-valuenow`, `aria-valuetext`, `aria-valuemin` or `aria-valuemax`; it is deliberately a plain text box for screen readers, with the group carrying `aria-invalid` and the value conveyed by the text itself. [react-aria, base-ui] (decision needed)

### Keyboard

- [ ] `number-field.keyboard.1` Given focus on the field, when ArrowUp is pressed the value MUST increase by one step and when ArrowDown is pressed it MUST decrease by one step. [apg, kobalte, reka, zag, ark, base-ui, react-aria]
- [ ] `number-field.keyboard.2` Given a minimum, when Home is pressed the value MUST be set to that minimum; given a maximum, when End is pressed it MUST be set to that maximum. [apg, kobalte, reka, zag, base-ui, react-aria]
- [ ] `number-field.keyboard.3` Given a step grid and bounds, when End is pressed then the value goes to the largest step-aligned value within the maximum (step 10 with max 521 gives 520), and Home goes to the minimum. [react-aria] (candidate)
- [ ] `number-field.keyboard.4` Given no minimum or maximum, when Home or End is pressed, then `preventDefault` is NOT called, leaving native caret movement intact. [base-ui] (candidate)
- [ ] `number-field.keyboard.5` Given a key the field handles, then the handler MUST call `preventDefault` so the arrow key does not also scroll the page or move the text cursor. [apg]
- [ ] `number-field.keyboard.6` Given a field whose text is directly editable, then all standard single-line text editing keys for the platform MUST keep working: Backspace, Delete, ArrowLeft, ArrowRight, Tab and Enter MUST NOT be canceled, and neither may keys the field does not handle such as PageUp, PageDown, Insert and F5. [apg, base-ui]
- [ ] `number-field.keyboard.7` Given a disallowed printable character, when it is typed, then neither the field contents nor the value MUST change; typing a letter leaves the input untouched. [apg, base-ui, zag, reka]
- [ ] `number-field.keyboard.8` Given Enter, then it commits like a blur: the typed text is parsed, the value is reformatted in place, and stepping still works afterwards. [reka, zag, react-aria]
- [ ] `number-field.keyboard.9` Given an empty field, when an arrow key is pressed, then the first step lands on a documented seed per bound combination: unbounded starts at 0 both ways; `min: -5` gives -5 up and 0 down; `min: 5` gives 5 both ways; `max: 5` gives 0 up and 5 down; `max: -5` gives -5 both ways; -5..5 gives -5 up and 5 down; -15..-5 gives -15 up and -5 down; 5..15 gives 5 up and 15 down. [react-aria] (candidate)
- [ ] `number-field.keyboard.10` Given an empty field with a step, then the first arrow press snaps the seed onto the step grid within the bounds: with `min: 2` and `step: 3` the value climbs 2, 5, 8 (the first step lands on the minimum rather than minimum plus step). [reka, react-aria]
- [ ] `number-field.keyboard.11` Given a fully negative range, then the seed on the first step is the in-range value nearest zero (the maximum), not zero and not the directionally snapped value. [base-ui] (candidate)
- [ ] `number-field.keyboard.12` Given a held arrow key producing repeat keydown events, then each repeat applies exactly one step. [react-aria] (candidate)
- [ ] `number-field.keyboard.13` Given a value with more precision than the display shows, then arrow keys step the full-precision numeric state rather than the rounded display text: 1.23456 steps to 2.23456, not 2.235, and this survives a no-edit focus and blur cycle. [base-ui] (candidate)
- [ ] `number-field.keyboard.14` Given a controlled value the parent never mirrors back, then an arrow key steps from the dirty input text rather than the stale numeric state, and a non-mutating key such as ArrowLeft in between MUST NOT mark the input as synced. [base-ui] (candidate)
- [ ] `number-field.keyboard.15` Given a consumer key handler that calls `preventDefault`, then the field does not step and no change callback fires. [base-ui] (candidate)
- [ ] `number-field.keyboard.16` Given a keydown with the IME composition key code 229, then `preventDefault` MUST NOT be called. [base-ui] (candidate)
- [ ] `number-field.keyboard.17` Given a locale whose decimal separator is a comma, then the first comma keydown is allowed and a second one is blocked while the group separator stays allowed repeatedly; a locale with space-like grouping allows the space key. [base-ui] (candidate)
- [ ] `number-field.keyboard.18` Given a value that already carries a sign, then a second minus keydown is blocked unless the existing sign or the whole value is selected. [base-ui] (candidate)
- [ ] `number-field.keyboard.19` Given a percent format, then Unicode plus and minus, permille and fullwidth digit keydowns are allowed; with no percent format, the percent and permille keys are blocked. [base-ui] (candidate)
- [ ] `number-field.keyboard.20` Given a decimal separator typed over a selection that spans the existing separator, then the keydown is allowed. [base-ui] (candidate)
- [ ] `number-field.keyboard.21` Given a spinbutton primitive with paged handlers, when PageUp or PageDown is pressed then the paged handler fires once; with no paged handler it falls back to the single-step handler, and Home and End fire the to-minimum and to-maximum handlers. [react-aria, kobalte]
- [ ] `number-field.keyboard.22` Divergence: the large step is bound to Page Up and Page Down, which MAY change the value by more than one step; the APG quantity example implements neither key, and the APG date example uses 5 for day, month and year. `largeStep` defaults to ten times `step`. [apg, kobalte, react-aria] (decision needed)
- [ ] `number-field.keyboard.23` Divergence: the large step is bound to Shift plus an arrow key and the small step to Alt plus an arrow key, with `largeStep` defaulting to ten times `step` and `smallStep` to `step` divided by 10; a bare arrow key uses the ordinary step even when `largeStep` is set, and Page Up and Page Down are left unhandled. [zag, ark, base-ui] (decision needed)

### Pointer

- [ ] `number-field.pointer.1` Given increment and decrement buttons, when one is clicked, then the value MUST change by a single step, not the large step. [apg, kobalte, reka, zag, ark, base-ui, react-aria]
- [ ] `number-field.pointer.2` Given a held stepper button, then the first step fires immediately, then nothing until a start delay elapses, after which steps repeat on a fixed interval; releasing stops it. [react-aria, base-ui, zag]
- [ ] `number-field.pointer.3` Given a hold that reaches a bound, then auto-stepping stops there and fires no further change callbacks, and the release still commits once with the boundary value. [react-aria, base-ui]
- [ ] `number-field.pointer.4` Given a hold, when the pointer leaves the button, then stepping stops; re-entering while still held resumes it, but re-entering after release does NOT. [base-ui] (candidate)
- [ ] `number-field.pointer.5` Given a stepper activated by pointerdown followed by pointerup and click, then the value changes exactly once, never twice. [base-ui] (candidate)
- [ ] `number-field.pointer.6` Given a non-primary pointer button (middle or right), then the press neither syncs dirty text nor starts a hold nor changes the value. [base-ui] (candidate)
- [ ] `number-field.pointer.7` Given a pen pointer, then it is treated like touch rather than mouse, so the input does not take focus on press. [base-ui] (candidate)
- [ ] `number-field.pointer.8` Given a quick touch tap on a stepper, including the compatibility mouse events the browser synthesizes afterwards, then the value changes exactly once and the commit callback fires once. [base-ui] (candidate)
- [ ] `number-field.pointer.9` Given the field becomes disabled mid-hold, then the hold is canceled, further ticks do nothing, re-enabling does not resume it, and the pending touch compatibility click is swallowed. [base-ui] (candidate)
- [ ] `number-field.pointer.10` Given a stepper activated by a programmatic `click()` with no pointer events, which is the screen reader and automation path, then the value still changes by one step. [react-aria] (candidate)
- [ ] `number-field.pointer.11` Given a stepper whose button becomes disabled during an auto-spin, then the spin stops rather than continuing against a disabled control. [react-aria] (candidate)
- [ ] `number-field.pointer.12` Given uncommitted typed text and a stepper press, then the typed text is committed first and the step applies to it: typing 100 into a field showing 0 and clicking increment gives 101. [reka, base-ui, react-aria]
- [ ] `number-field.pointer.13` Given a disabled or read-only field, then clicking either stepper leaves the value unchanged and fires no change callback. [reka, base-ui]
- [ ] `number-field.pointer.14` Given a controlled value already at a bound, then pressing the stepper for that direction fires no change callback at all. [react-aria, base-ui]
- [ ] `number-field.pointer.15` Given a wheel event whose `ctrlKey` is true (the browser pinch-zoom gesture), then the value MUST NOT change. [react-aria, base-ui]
- [ ] `number-field.pointer.16` Given an unfocused input, then a wheel event over it MUST NOT change the value, so scrolling the page is safe. [react-aria, base-ui]
- [ ] `number-field.pointer.17` Given a horizontal-only wheel event, then it is left uncanceled so the page scrolls and no value change or commit fires; a vertical wheel event carrying horizontal noise still scrubs, the dominant axis winning. [base-ui] (candidate)
- [ ] `number-field.pointer.18` Given Shift held during a wheel event, then the wheel steps by the large step, including when the browser swaps the wheel axis and delivers the delta horizontally as Chromium does. [base-ui] (candidate)
- [ ] `number-field.pointer.19` Given a wheel step, then it fires both the change and the commit callbacks once with a wheel reason, a later blur does not commit again, and a wheel step that is a no-op at a bound commits nothing. [base-ui] (candidate)
- [ ] `number-field.pointer.20` Given a scrub area, when the pointer is pressed and dragged, then the value changes by one unit per pixel along the scrub direction, the root carries `data-scrubbing` while the drag lasts, the change callback fires during the drag and the commit callback fires once on release with the final value. [base-ui, zag]
- [ ] `number-field.pointer.21` Given a scrub area with a pixel sensitivity, then the value only steps once the accumulated movement reaches that threshold and the remainder carries over; a zero-distance move never steps, so it cannot snap an off-grid value. [base-ui] (candidate)
- [ ] `number-field.pointer.22` Given a scrub direction, then movement along the other axis is ignored entirely. [base-ui] (candidate)
- [ ] `number-field.pointer.23` Given a scrub area press, then a non-primary button and a read-only field never start a scrub; a single-touch `touchstart` is canceled to block page scroll while a two-touch gesture is left to the browser for pinch-zoom. [base-ui] (candidate)
- [ ] `number-field.pointer.24` Given a scrub that has ended, then further pointer movement is ignored, and the scrub does not resume when a hidden scrub area is revealed again. [base-ui] (candidate)
- [ ] `number-field.pointer.25` Given a scrub area clicked without movement, then its click handler fires exactly once, and a click on a child element fires both the child's handler and the scrub area's. [base-ui] (candidate)
- [ ] `number-field.pointer.26` Given the scrub area unmounts mid-scrub, then the root loses `data-scrubbing` rather than staying stuck. [base-ui] (candidate)
- [ ] `number-field.pointer.27` Given a virtual scrub cursor, then it renders only for mouse input and only for the active scrub area, never for touch; it does not render when pointer lock is denied or resolves after the release, and its transform tracks the visual viewport scale (scale 2 gives `scale(0.5)`). [base-ui] (candidate) (browser-only)
- [ ] `number-field.pointer.28` Given a scrub past the allowed bounds with a teleport distance, then the virtual cursor wraps around to the opposite side. [base-ui] (candidate) (browser-only)
- [ ] `number-field.pointer.29` Given Firefox, then the pointer lock release is deferred by 20 ms after the pointer is released so soft clicks are not swallowed; the commit fires and `data-scrubbing` clears only after that delay. [base-ui] (candidate) (firefox-only)
- [ ] `number-field.pointer.30` Given an APG spinbutton with a paired `output` announcer, then clicking a stepper MUST update the `output` with the new value while arrow keys MUST NOT, because the field value is already announced on change; the announcer MUST self-clear after a delay, 2000 ms in the APG quantity example. [apg]
- [ ] `number-field.pointer.31` Divergence: the mouse wheel changes the value whenever the input is focused, with no opt-in prop, and is turned off by an opt-out prop. [reka, react-aria] (decision needed)
- [ ] `number-field.pointer.32` Divergence: the mouse wheel changes the value only when an opt-in prop is set, and is inert otherwise even while focused. [base-ui, zag] (decision needed)
- [ ] `number-field.pointer.33` Divergence: a positive `deltaY` (scrolling down) INCREMENTS the value and a negative one decrements it; an inversion prop swaps them. [reka, react-aria] (decision needed)
- [ ] `number-field.pointer.34` Divergence: a positive `deltaY` DECREMENTS the value and a negative one increments it, matching the direction the content would move. [base-ui] (decision needed)
- [ ] `number-field.pointer.35` Divergence: press-and-hold auto-repeat starts after 400 ms and then steps every 60 ms. [react-aria, base-ui] (decision needed)
- [ ] `number-field.pointer.36` Divergence: press-and-hold auto-repeat starts after 300 ms and then steps every 50 ms. [zag] (decision needed)

### Focus management

- [ ] `number-field.focus-management.1` Given a number field, then focus MUST remain on the text field throughout operation, including while the steppers are used, and the steppers MUST NOT be reachable by Tab (`tabindex="-1"`) because the arrow keys already provide their function. [apg, react-aria, zag]
- [ ] `number-field.focus-management.2` Given a stepper press, then focus moves to (or stays on) the input rather than the button, and the blur callback does not fire, so stepping never looks like leaving the field. [kobalte, base-ui, react-aria]
- [ ] `number-field.focus-management.3` Given a mouse press on a stepper that focuses the input, then the caret is placed at the end of the value, unless a consumer focus handler sets its own selection, which survives. [base-ui] (candidate)
- [ ] `number-field.focus-management.4` Given a focus-on-change opt-out, then clicking a stepper leaves focus where it was. [reka] (candidate)
- [ ] `number-field.focus-management.5` Given a read-only field, then it stays in the tab order and can be focused. [reka] (candidate)
- [ ] `number-field.focus-management.6` Given a number field inside a field wrapper, when the label is clicked, then the visible input receives focus. [ark, base-ui]
- [ ] `number-field.focus-management.7` Given the hidden form input is focused (as browser autofill or a form label can do), then focus is forwarded to the visible input with the caret at the end, unless a consumer focus handler sets its own selection. [base-ui] (candidate)
- [ ] `number-field.focus-management.8` Given focus arriving by Tab with the browser's own selection of the whole value, then the library does not override it. [base-ui] (candidate)
- [ ] `number-field.focus-management.9` Given a consumer focus handler that calls `preventDefault`, then the field's focused state is not set even though the DOM focus moved. [base-ui] (candidate)
- [ ] `number-field.focus-management.10` Given a typed value and Tab out of the field, then the change callback fires before the blur callback. [react-aria] (candidate)
- [ ] `number-field.focus-management.11` Given focus entering a field with a value, then the existing text should be selected so the first keystroke replaces it; react-aria's test for this is disabled because jsdom does not implement text selection, so it needs a browser-mode test. [react-aria] (candidate) (browser-only)

### State

- [ ] `number-field.state.1` Given a value typed into the field, then the change callback carries the parsed number and the display keeps the raw text until a commit; a controlled field whose parent rejects the value snaps the display back. [kobalte, reka, base-ui, react-aria]
- [ ] `number-field.state.2` Given a default value, then the input shows it on mount and no change callback fires; `0` renders as `"0"` rather than an empty string. [kobalte, reka, base-ui, react-aria]
- [ ] `number-field.state.3` Given a cleared field, then the value is reported as empty (`null`, or NaN in react-aria) rather than as zero, and an untrimmed whitespace-only value is also empty. [base-ui, react-aria, zag]
- [ ] `number-field.state.4` Given a bare sign or a bare decimal separator in the field, then it is not parseable: no change callback fires and a blur commits nothing. [base-ui, react-aria]
- [ ] `number-field.state.5` Given progressive typing, then the change callback fires once per parseable state: `1`, `12`, `12.`, `12.a` reports 1, 12, 12 (the trailing separator parses as 12 and the non-numeric tail is ignored) and nothing commits until blur. [base-ui] (candidate)
- [ ] `number-field.state.6` Given a change reason, then it distinguishes typing (`input-change`), clearing (`input-clear`), pasting (`input-paste`), keyboard stepping (`keyboard`), increment and decrement presses, wheel and scrub, and the details event type narrows per reason. [base-ui] (candidate)
- [ ] `number-field.state.7` Given a change callback that cancels the change, then the value stays, nothing commits, and a canceled step after an external change MUST NOT re-commit the stale earlier value. [base-ui] (candidate)
- [ ] `number-field.state.8` Given a commit (blur, Enter, stepper release, wheel or scrub end), then the commit callback fires once with the final, clamped value, and never fires for a blur of an untouched field or for an unparseable value. [base-ui] (candidate)
- [ ] `number-field.state.9` Given a value or default value outside the range, then the rendered value is clamped, and with a step it is also snapped (default 20 with `max: 10` and `step: 3` renders 9). [react-aria] (candidate)
- [ ] `number-field.state.10` Given a step, then the value MUST NOT drift on repeated stepping: `step: 0.001` from 1 yields exactly 1.001, 1.002, 1.003, 1.004, `min: 0.1 max: 24 step: 0.1` shows exactly 24, and 0.7 plus 0.1 is exactly 0.8 rather than 0.7999999999999999. [react-aria, base-ui, zag]
- [ ] `number-field.state.11` Given step snapping, then an off-grid value moves to the next grid line rather than adding a full step (18.98 increments to 19, 18.11 decrements to 18) while an on-grid value moves a full step; snapping is anchored on the minimum when one is set, and a non-step-aligned bound stays reachable (`min: 2 max: 21 step: 3` reaches 20 and stops, `max: 10 step: 3` from 13 clamps to 10 rather than snapping to 9). [reka, base-ui, react-aria]
- [ ] `number-field.state.12` Given step snapping disabled, then the exact step is added with no rounding (2.7 with `step: 2` gives 4.7) and the typed value is kept as typed. [reka, base-ui]
- [ ] `number-field.state.13` Given a small step (the Alt modifier), then snapping rounds to the NEAREST multiple rather than directionally: 0.15 with a 0.1 small step gives 0.2, and -0.15 gives -0.2. [base-ui] (candidate)
- [ ] `number-field.state.14` Given a step finer than the display precision, for example 0.0001, then the reported value advances by it even while the displayed text is unchanged. [base-ui] (candidate)
- [ ] `number-field.state.15` Given an empty or NaN fallback with a range that excludes zero, then the fallback is clamped into range (`max: -5` seeds -5). [reka, base-ui]
- [ ] `number-field.state.16` Given a repeated edit whose parsed number is unchanged, then the display is corrected but no second change callback fires. [react-aria] (candidate)
- [ ] `number-field.state.17` Given an external value change while the user is typing, then the display switches to the externally formatted value immediately and keeps it after blur. [base-ui] (candidate)
- [ ] `number-field.state.18` Given an external value change after a step, then the input shows the new external value rather than the stepped one, and a first step after it applies to the external value. [base-ui] (candidate)
- [ ] `number-field.state.19` Given a controlled value that is set to null, then the input becomes empty. [react-aria, base-ui]

### Notes and edge cases

- [ ] `number-field.notes-and-edge-cases.1` Given text editing inside a spinbutton, then the most robust implementation relies on the browser's own editing behavior for `input[type="text"]` or a `contenteditable` element rather than reimplementing it, and a spinbutton with a large range SHOULD support both a small and a large step, for example 1 minute on an arrow key and 10 on the paged key. [apg]
- [ ] `number-field.notes-and-edge-cases.2` Given a spinbutton whose maximum depends on another spinbutton, as a day depends on month and year, then the maximum MUST be recomputed on every dependency change and the current value forced down when it now exceeds that maximum. [apg]
- [ ] `number-field.notes-and-edge-cases.3` Given a spinbutton configured to wrap, then exceeding the maximum MUST wrap to the minimum and falling below the minimum MUST wrap to the maximum, including when a large step overshoots by a non-exact amount (a day at 27 with step 5 and max 31 lands on 1); the APG date example wraps day and month and explicitly disables wrapping on year. [apg]
- [ ] `number-field.notes-and-edge-cases.4` Given non-numeric text such as "abc" or a bare space typed into the APG quantity spinbutton, then the value MUST resolve to the minimum. [apg]
- [ ] `number-field.notes-and-edge-cases.5` Given a paste, then it inserts at the caret (or replaces the selected range) rather than replacing the whole value, leaves the caret just after the pasted text, and is rejected outright when it does not parse; a read-only field never accepts it. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.6` Given a paste whose clipboard read throws, then the value is unchanged, the event is left un-prevented, and exactly one development warning names the failed clipboard read; a paste event with no clipboard data reports the unchanged value once with a paste reason. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.7` Given a caret inside a formatted prefix or suffix such as a currency code, then a `beforeinput` delete is allowed when the whole symbol is selected and canceled when only part of it is or the caret is inside it; digit insertion is allowed inside the numeric part and canceled inside the symbol; `historyUndo` and `historyRedo` are always allowed so browser undo keeps working; and a leading sign can be deleted. [react-aria] (candidate)
- [ ] `number-field.notes-and-edge-cases.8` Given a reformat that changes the text around the caret, then the caret is mapped through the change rather than jumping to the end: with a currency format, typing a digit at index 4 of `$555.00` gives `$5555.00` with the caret at 5, and blurring regroups to `$5,555.00`. The mapping rule is prefix-and-suffix matching, with a fallback to the same relative position: an unchanged value keeps the caret, appended characters keep it at the end of the shared prefix, prepended characters shift it right by the inserted count, grouping separators shift it (`1000` to `1,000` moves index 4 to 5 and index 2 to 3), a caret past the new end clamps to the end, an emptied value returns it to 0, and a partial prefix or suffix match clamps to the matched length. [zag] (candidate)
- [ ] `number-field.notes-and-edge-cases.9` Given caret-adjacent deletions in formatted text, then the separator and sign characters are deletable in place: deleting before or backspacing after the decimal separator removes it (`123.45` becomes `12345`), the same holds for the minus sign, and deleting digits either side of the separator keeps the rest intact. [zag] (candidate)
- [ ] `number-field.notes-and-edge-cases.10` Given a selection replacement, then only the selected characters are replaced and non-numeric characters in the replacement are filtered: `100.25` with `100` selected and `200` typed gives `200.25`, and with `abc456def` typed gives `456.45` from `123.45`. [zag] (candidate)
- [ ] `number-field.notes-and-edge-cases.11` Given leading zeros, then the raw text is preserved while editing (`007` stays `007`, Backspace steps `00`, `0`, ``) and normalizes on commit (`007` to 7, `000.45` to 0.45, `000` to 0), while `0.123` is left alone; negative zero is preserved deliberately (`-0` stays `-0`, `+0` becomes `0`, `-0.0` stays `-0`). [zag] (candidate)
- [ ] `number-field.notes-and-edge-cases.12` Given invalid character sequences typed, then only the valid parts survive: `--5` becomes `-5`, `1a2b3` becomes `123`, `1.5x` becomes `1.5`, `123-` becomes `123`, `5.-` keeps the trailing separator as `5.`, and a second decimal separator is dropped (`1.23` plus `.45` gives `1.2345`). [zag] (candidate)
- [ ] `number-field.notes-and-edge-cases.13` Given an invalid value left in the field on blur, then the display reverts to the last good value and no change fires (a lone minus from a default of 10 reverts to 10, and `-€1.00` edited down to `-` reverts). [react-aria] (candidate)
- [ ] `number-field.notes-and-edge-cases.14` Given a float-cleanup step, then it removes binary noise without destroying precision: `0.2 + 0.1` gives exactly 0.3, `-0.1 - 0.2` gives -0.3, `0.1 + 0.7` gives 0.8, values finer than three fraction digits and safe integers are returned unchanged, non-finite values pass through untouched, and a sum whose single ULP exceeds the cleanup delta (from the 2^19 binade up, for example `1000000.1 + 0.2`) is left as the raw noisy sum. [base-ui, zag]
- [ ] `number-field.notes-and-edge-cases.15` Given format options on the cleanup step, then rounding resolves against the format: an explicit maximum fraction digits rounds and writes back to the numeric value, `roundingMode` is honored including half-even ties and the floor-versus-trunc difference on negatives, `roundingIncrement` and significant digits are applied, percent values round at display scale (times 100) while `style: 'unit'` percent and currency are not scaled, compact and scientific notation round against standard notation and decline to act when the rounded form is not invertible, and a value already on the precision boundary is never nudged. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.16` Given the value-validation step, then its order is: clamp into range, snap to the step grid (directionally for a normal step, to the nearest multiple for a small step, anchored on the minimum), apply the format's rounding, then clamp again so a non-step-aligned bound stays reachable. A positive step snaps down to the multiple below and a negative step up to the multiple above (5.5 gives 5 with step 1 and 6 with step -1), clamping can be disabled for out-of-range entry, and fractional steps do not get stuck (`100.1 + 0.1` lands on 100.2, not back on 100.1). [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.17` Given the step helpers, then `snapValueToStep` anchors the grid at the minimum (or at 0 when the minimum is undefined) and clamps into range: 2 with `min: -0.5 step: 3` gives 2.5, 106.2 with `max: 100` gives 99.5, -8 with step 5 gives -10, 240 in 0..100 with step 200 clamps to 100, 23 gives 20 and 27 gives 30. `roundToStepPrecision` returns the input unchanged for integer steps, rounds to the step's decimal places for fractional steps (2.349 with step 0.1 gives 2.35), and follows the exponent for exponential steps (0.123456789 with 1e-3 gives 0.1235, with 1e-8 unchanged). [react-aria, zag]
- [ ] `number-field.notes-and-edge-cases.18` Given the locale parser, then it parses each locale's own formatting back to a number: de-DE `1.234,56` gives 1234.56, prefix and suffix currency symbols both parse, unit strings such as `12 km/h` parse, consecutive separators collapse with only the last dot acting as the decimal (`1..5` gives 1.5, `123..456..789.01` gives 123456789.01), the full 0-9 range of Persian, fullwidth, Arabic-Indic and Han digits maps (both Han zero forms give 0), `Infinity` with an explicit sign returns null, and the numeral-character test accepts only digits, rejecting `.`, `,`, `-`, `+`, `%`, the Arabic decimal separator and letters. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.19` Given accounting-style parentheses typed into base-ui, then the value is invalid and nothing is reported, unlike react-aria which parses them as negative; a spec test MUST state which behavior it asserts. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.20` Given format options passed as a fresh object literal on every render, then an uncommitted typed value MUST survive the rerender; only a real content change reformats the display (EUR to USD reformats, an identical object or an undefined-to-undefined rerender does not). [react-aria] (candidate)
- [ ] `number-field.notes-and-edge-cases.21` Given a part rendered with no root ancestor, then it throws a named context error, and the scrub cursor throws its own when rendered outside the scrub area. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.22` Given a hold in progress when the tree unmounts, then the global pointerup listener is removed with the same handler and options it was registered with. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.23` Given a consumer blur handler that calls `preventDefault`, then the field neither reformats, nor marks itself touched, nor commits; a change event whose native default was already prevented is ignored. [base-ui] (candidate)
- [ ] `number-field.notes-and-edge-cases.24` Given a conformance harness for a number field, then it needs the input, both triggers and the scrubber as locators, an atomic fill and a key-at-a-time typing path (they exercise different code), an approximate value assertion for hold-spinning, `aria-invalid` and `checkValidity()` assertions, select-all, a scrub helper that presses, moves in steps and releases, a tick helper matching the spin interval plus the initial delay, and a way to hold a trigger down without releasing. [zag] (candidate)

## Deferred

- Whether the input is a `spinbutton` (`number-field.roles-and-attributes.26` and `.27`). This is the first decision to make: it determines whether the suite asserts `aria-valuenow` at all. The APG and axe say spinbutton; react-aria and base-ui deliberately expose a plain text box because a spinbutton role makes screen readers read the value instead of letting the user edit the text. Both camps have a real argument and the spec cannot assert both.
- Large-step key binding (`number-field.keyboard.22` and `.23`). Page Up and Page Down versus Shift plus arrow. They can coexist, and probably should, but the default `largeStep` and `smallStep` values and which modifier maps to which need settling first.
- Out-of-range typed values (`number-field.state.25` and `.26`) and off-grid typed values (`.27` and `.28`). Clamp silently, or keep the text and go invalid. These two decisions travel together and drive the whole commit path.
- Empty on blur (`number-field.state.29` and `.30`). Stay empty or reset to the minimum. Staying empty is what users expect from a form field; resetting is what the APG example does.
- Wheel behavior (`number-field.pointer.31` through `.34`). Two questions: whether the wheel is on by default, and which sign increments. Getting the sign wrong is worse than not supporting the wheel at all.
- Auto-repeat timings (`number-field.pointer.35` and `.36`). 400/60 versus 300/50. Any choice needs the harness to control the clock, so the suite should read the delays from the implementation rather than hard-coding them.
- Scrub-to-change. Only base-ui and zag have it, and zag's e2e test for it is skipped. The pointer-lock, visual-viewport-scale, teleport-wrap and Firefox-delay behaviors are real but need a browser-mode suite; `number-field.pointer.20` through `.29` are recorded so the work is scoped, not so it blocks the component.
- The `removeFloatingPointErrors` and `toValidatedNumber` contracts (`number-field.notes-and-edge-cases.14` through `.18`). These are unit-testable pure functions and belong in `packages/core` tests rather than the conformance suite; they are recorded here because the observable rounding behavior they produce is part of the component contract.
- Caret mapping through a reformat (`number-field.notes-and-edge-cases.8`). Only zag specifies it, in enough detail to implement. It needs a decision on whether the caret contract is part of conformance or an implementation detail, since asserting it requires selection APIs that jsdom only partly supports.
- Wrapping spinbuttons (`number-field.notes-and-edge-cases.3`). No library implements wrap-around; only the APG date example does. If we want it, it needs a prop and its own bullets.
- The dependent-maximum case (`number-field.notes-and-edge-cases.2`). This is really a date-field concern and may move to that spec file.
